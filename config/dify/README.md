# Dify 应用配置

这里放 Dify 应用的导出文件（DSL）。应用里不写死任何地址和密钥，地址、Token 用环境变量，导入后在 Dify 里填写。

## 模型和兜底（三个应用都一样）

模型节点（判断意图、提取参数、写回答）不是只接一家：失败先重试一次，再换 `models.json` 里 `chain` 的下一家；都失败时，**判断意图改用关键词规则**（查余额、查职责、查请假、查待审批、询盘列表这些不需要模型的功能照常可用），其他节点回复一句“AI 服务暂时不可用”（制度问答会附上检索到的制度标题），对话不报错。

- 默认 `chain`：通义千问 `qwen-plus` → DeepSeek `deepseek-v4-flash`。
- **`chain` 里每一家都必须在 Dify 装好插件、录好 Key。** Dify 在每次对话开始时检查所有模型节点，缺插件或缺 Key 时整个应用直接报错（本地实测）。所以只放已经有 Key 的厂商。
- 想多加一家（例如智谱 `glm-4.5-air`、Kimi、豆包接入点）或换顺序：改 `models.json` 的 `chain`，在仓库根目录运行 `uv run --with ruamel.yaml python config/dify/model_fallback.py`，重新导入三个 DSL。`providers` 里列了允许使用的国产厂商插件（通义、DeepSeek、智谱、豆包、Kimi、MiniMax、混元、文心、硅基流动、百川、阶跃、华为云，以及自建模型用的 OpenAI 兼容接口 / Xinference / Ollama），CI 会拒绝其他厂商。
- 关键词规则和各节点的兜底回复也在 `models.json` 的 `fallbacks` 里，按顺序匹配（正则）。
- 生成的节点 id 带 `__`（`__m2` 备用模型、`__agg` 汇合、`__kw` 关键词、`__down` 兜底回复），手改 DSL 时不要用这个分隔符；脚本可以重复运行。
- 在 Dify 后台手动换了某个节点的模型，下次重新导入会被仓库版本覆盖；要长期换就改 `models.json`。

员工一分钟内消息太多时（X4 按员工限流，默认 20 条/分钟），HR 助手和询盘助手直接回复“消息太多了，请一分钟后再试”，不调模型；X4 连不上时回复“系统暂时不可用”，不再往下走（以前会继续走、查不到数据时误答“没有假期额度”）。

### 测试情况（2026-10-31，本地 Dify 1.17.1）

用 OpenAI 兼容插件接一个假模型服务（可以按模型名让它返回 500），X3、X4 用测试替身，三个应用都按生成脚本导入：

- 主模型返回 500、备用正常：查余额、查职责、问制度、起草并确认请假、询盘列表和统计都正常，日志里每次先调主模型、再调备用。
- 主备都 500：查余额、查职责、询盘列表照常（关键词规则）；问制度回复“AI 服务暂时不可用”并附《年假规定》；起草请假、询盘统计回复对应的固定话。
- 三级 `chain`（前两家 500、第三家正常）：都由第三家接上。
- `chain` 里放一个没录 Key 的模型：三个应用每次对话都直接 400，确认上面“每一家都要有 Key”的要求。
- X4 限流设成 3 条/分钟：同一员工第 4 条收到“消息太多了”，没有调模型；停掉 X4：收到“系统暂时不可用”。
- 真实通义、DeepSeek 的回答质量要等 Key 到位后测。

## 制度问答（`policy-qa.yml`）

员工在企业微信里问公司制度，只在他的岗位可见的知识空间里检索，回答附出处。

流程：`开始 → 按岗位检索（HTTP 调 X3）→ 整理检索结果（代码）→ 有没有检索到`

- 检索到：交给“制度问答”模型节点，只根据检索内容回答、每个要点标 [编号]，最后附出处列表。
- 没检索到、提问人不是在职员工、X3 不可用：直接回复原因，不调模型，避免模型编造制度。

身份只取 `sys.user_id`（dify-on-wechat 传入的企业微信 userid），模型改不了，见 `docs/adr/0001-身份传递.md`。

### 导入步骤

1. 在 Dify 装好 `models.json` 的 `chain` 里每一家的模型插件（默认通义千问、DeepSeek），在“模型供应商”里录入 Key（Key 只在后台录入）。
2. “工作室 → 导入 DSL 文件”，选 `policy-qa.yml`。
3. 打开应用的“环境变量”，填写：
   - `x3_url`：X3 地址，默认 `http://kb-gateway:8080`
   - `x3_token`：X3 的 `EB_KB_SERVICE_TOKEN`（密钥类型，导出时不会带出）
4. 想换模型或加备用模型时改 `models.json` 再重新生成（见上面“模型和兜底”），提示词不用改。
5. 发布，把应用 API Key 配给 dify-on-wechat（`dify_app_type` 用 `chatbot`）。

### 部署要求

Dify 默认禁止访问内网地址。要让 Dify 的 SSRF 代理放行 X3，在部署配置里设置 `SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=kb-gateway`（或 `SSRF_PROXY_ALLOW_PRIVATE_IPS` 只放行 X3 的地址），并重建 `ssrf_proxy` 容器。只设在 api 容器上不生效，检查是在 ssrf_proxy 里做的。

### 测试情况（2026-10-16，本地 Dify 1.17.1）

- 原样导入成功（模型插件没装也能导入，装好后在节点里选模型）。
- 把模型节点换成假节点后，用真实 X3、Frappe 和 X5 同步的文档跑通：
  - 张三（销售代表）问年假，答案附《年假规定》
  - 李四（人事部 HRBP）问薪酬核算，答案附《薪酬核算细则》
  - 张三问薪酬核算，收到“没有找到相关制度”，看不到人事文档
  - 非在职员工收到“未找到你的在职员工信息”
  - 停掉 X3，收到“知识库检索暂时不可用”，对话不报错
- 模型回答的质量（是否只用检索内容、出处标注）要等模型 Key 到位后实测。

## HR 助手（`hr-assistant.yml`）

员工在企业微信里和 HR 助手对话：问制度、查假期余额、查自己的请假进度、查等自己审批的请假、查自己的岗位职责、发起请假。包含了制度问答的全部节点，上线时企业微信接这个应用即可（制度问答应用可以只留着单独测试）。

流程：

1. 员工回复的正好是“确认请假”：
   - 会话变量 `leave_draft` 里有草稿：HTTP 调 X4 `/v1/leave/confirm` 提交，清空草稿，回复结果。整条路不经过模型。
   - 没有草稿（别人的会话、已提交过、已过期）：提示“没有等你确认的请假”。
2. 其他消息：HTTP 调 X4 `/v1/session` 换会话令牌，再用“判断意图”分类：
   - 问制度：走制度问答（X3 按岗位检索 → 模型只根据检索内容回答 → 附出处）。
   - 查余额、查我的请假、查待我审批、查岗位职责：调 X4 的 MCP 工具，用代码节点整理成文字回复，不经过模型，模型看不到这些数据。
   - 发起请假：“提取请假信息”节点让模型抽出假期类型、起止日期、事由（提示里给了北京时间今天的日期），调 X4 `draft_leave` 起草，草稿存进 `leave_draft`，回复草稿请员工核对。
   - 其他：说明能做什么。

身份只取 `sys.user_id`。模型只参与意图分类、参数提取和制度回答，查谁、提交什么都由工作流和 X4 决定，见 `docs/adr/0001-身份传递.md`。

### 导入步骤

1. 装好 `chain` 里每一家的模型插件并录入 Key（默认通义千问、DeepSeek；“判断意图”“提取请假信息”“制度问答”和它们的备用节点用到）。
2. “工具 → MCP → 添加 MCP 服务”：地址 `http://frappe-mcp:8080/mcp/`，**服务标识填 `eb-hr`**（应用里的工具节点按这个标识找服务），请求头 `Authorization: Bearer <EB_MCP_SERVICE_TOKEN>`。
3. 导入 `hr-assistant.yml`，在“环境变量”里填：`x3_url`、`x3_token`（同制度问答），`x4_url`（默认 `http://frappe-mcp:8080`）、`x4_token`（X4 的 `EB_MCP_SERVICE_TOKEN`）。
4. 发布，把应用 API Key 配给 dify-on-wechat（`dify_app_type` 用 `chatbot`）。草稿存在 Dify 会话里，要求 dify-on-wechat 对同一个员工连续的消息沿用同一个会话；企业微信实测时要确认这一点。

部署时 SSRF 代理除了 X3，还要放行 X4（`frappe-mcp`）。

X4 或 X3 连不上时，对话不报错，员工收到“暂时不可用”。

### 测试情况（2026-10-16，本地 Dify 1.17.1）

- 原样导入成功。
- 把三个模型节点换成规则节点后，用真实 X3、X4、Frappe HR 跑通全部路径：
  - 张三查余额：“年假：剩余 5 天（总额 5，已休 0，审批中 2）”
  - 张三查请假进度、李四查待审批（显示申请人张三），都和 Frappe 一致
  - 张三问年假规定，答案附《年假规定》
  - 张三起草年假后回复“确认请假”，Frappe 里建出 Open 状态的请假单，审批人李四
  - 李四在自己的会话里说“确认请假”、张三再说一次“确认请假”：都提示没有待确认的请假，不会提交
  - 时间重叠时提示已有申请；假期类型不对时列出可选类型
  - 非在职员工收到“未找到你的在职员工信息”；MCP 服务没配好时收到“HR 系统暂时不可用”
  - 查岗位职责（P2-C1c，X4 用专用账号 eb-x4）：张三返回“销售代表”和 HR 在岗位上录的职责（富文本转成分行文字）；岗位没填职责、员工档案没有岗位、非在职员工各自收到对应提示
- 意图分类和参数提取的准确度要等模型 Key 到位后实测。
- 目前不按岗位开放不同工具：每个工具都只能查到员工本人的数据，没有越权风险，所有员工都能用全部工具。

## 询盘助手（`inquiry-assistant.yml`）

营销第一批，给销售和市场负责人用（说明见 `docs/营销询盘中心.md`）。Chatflow，先按 `sys.user_id` 向 X4 换会话令牌，再“判断意图”分 6 路：

- 我的询盘：调 X4 `my_inquiries`，列出分配给本人的未结询盘（按等级排）。
- 询盘详情：模型从这句话里提取询盘编号，调 `inquiry_detail`，给出需求、评分理由、来源和最近跟进。
- 写回复草稿：提取询盘编号和补充要求，调 `inquiry_detail` 拿需求，用需求去 X3 检索本人岗位能看的产品资料，再由“写回复草稿”节点写草稿。这个模型节点**没有工具**，提示词注明客户询盘里的指令一律不执行、价格交期等没资料的写【待确认】、不写客户联系方式。只出草稿，销售核对后自己发。
- 记跟进：提取编号、状态（跟进中/已回复/有意向/无效）和跟进内容，调 `follow_up_inquiry`，以本人身份保存。
- 询盘统计：提取天数（默认 30），调 `inquiry_stats`，按渠道、等级、AI 来源、状态汇总，再加按渠道和 AI 来源的转化（有效、转商机、成交、成交额），不含客户信息。
- 其他：说明能做什么。

工具返回里没有客户邮箱和电话；岗位没开“处理询盘”“查询盘统计”时 X4 直接拒绝，回复“没有开通”。

### 导入步骤

1. 模型同 HR 助手（“判断意图”、四个“提取”节点、“写回复草稿”用到）。
2. MCP 服务沿用 HR 助手的 `eb-hr`，在 Dify 里点一下“更新”，刷出 4 个询盘工具。
3. 导入 `inquiry-assistant.yml`，环境变量 `x3_url`、`x3_token`、`x4_url`、`x4_token` 同 HR 助手。
4. 发布，把应用 API Key 填进 `EB_PORTAL_DIFY_MARKETING_APP_KEY`，员工前台出现“询盘助手”。企业微信里要用的话，另配一个 dify-on-wechat 应用（第一批没做）。

### 测试情况（2026-10-30，本地 Dify 1.17.1）

- 原样导入成功（29 个节点、28 条边，4 个环境变量）。
- 没有模型 Key，模型节点没跑。7 个代码节点用真实 X4 返回逐个跑过：张伟（销售代表）列出 3 条询盘、看详情、记跟进改状态、写草稿前的检索词拼接都对；李娜（市场经理）出统计；王芳（出纳，未开通）收到“没有开通”；询盘不在本人名下时收到“不在你名下或已不存在”。
- 意图分类、参数提取和草稿质量要等模型 Key 到位后实测。
