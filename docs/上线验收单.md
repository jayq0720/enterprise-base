# 上线验收单（P3-C3）

目的：服务器到位后，按本单逐项验收，全部通过再进入试运行；试运行达到第 7 节的标准再正式上线。本单只列“要验什么、怎么算通过、谁负责”。具体操作步骤看 `docs/manual/` 里对应的手册，本单不重复。

填写方法：每项验完把 `[ ]` 改成 `[x]`，在行末写日期和证据位置（截图或日志摘要，去掉密钥、真实 userid 和员工信息）。不通过的写原因，交 Claude 排查。

负责人：**JQ** 准备外部条件和最终确认；**GPT** 部署和配置；**Claude** 测试、安全复核和问题修复。

## 1. 外部条件（JQ）

- [ ] 1.1 阿里云服务器到位，满足 `deploy/LOCAL.md` 的配置要求，开好 SSH 和 GitHub 访问。
- [ ] 1.2 服务器能拉到 GHCR 镜像（登录或改为公开镜像）。
- [ ] 1.3 已备案的域名，解析到服务器；企业微信后台的可信域名、可信 IP 填好。
- [ ] 1.4 模型 Key（百炼 / 方舟 / DeepSeek）申请好，只在 Dify 后台录入，不发到聊天里。
- [ ] 1.5 企业微信自建应用、通讯录同步权限开通，参数只写进服务器的 `deploy/secrets/`。
- [ ] 1.6 确认试运行范围：哪个部门、多少人、试运行几周。

## 2. 部署（GPT，Claude 复核）

- [ ] 2.1 按部署手册在服务器上从零起全套，所有容器健康；记录实际用时和镜像版本（对照 `deploy/VERSIONS.md`）。
- [ ] 2.2 `make -C deploy verify` 和部署校验在服务器上通过。
- [ ] 2.3 管理后台只能从 `EB_ADMIN_ALLOW_CIDRS` 里的地址打开；从别的网络访问被拒。
- [ ] 2.4 Dify 装好千问、豆包、DeepSeek 插件，没有装任何境外模型插件；HR 助手和制度问答能切换模型（`docs/manual/P0-模型插件验收.md`）。
- [ ] 2.5 X3、X4、X5 用 `main` 的发布镜像部署，三个接口账号是启用状态，Key 和 `.env` 一致。
- [ ] 2.6 重启全部容器后数据不丢。

## 3. 组织数据（HR 和 GPT）

- [ ] 3.1 用组织任职 Excel 导入真实部门、岗位、员工（`docs/manual/P1-组织任职导入操作.md`）；导入完删掉上传的原表。
- [ ] 3.2 **每个员工档案都填了岗位。** 没有岗位的员工用不了 HR 助手的任何工具。
- [ ] 3.3 每个员工都填了企业微信 userid，并和通讯录同步的结果一致。
- [ ] 3.4 每个岗位的岗位职责、可见知识空间、助手功能开关都按权限复核表（`docs/权限复核表.md`）配好，HR 抽查 3 个岗位。
- [ ] 3.5 请假两级审批：每个员工都有直属上级，HR 审批人不是任何人自己的主管。
- [ ] 3.6 入职模板按岗位配好，至少一个岗位有完整的入职活动。

## 4. 安全必做（Claude 复核，GPT 配置）

- [ ] 4.1 HR 助手和制度问答的 **Web App 已关闭**，只保留服务 API；用浏览器打开 Web App 网址确认不可用（`docs/manual/P1-HR助手部署与验收.md` 发布步骤）。每次重新导入应用或升级 Dify 后复查。
- [ ] 4.2 Dify 后台账号只开给 JQ 指定的系统管理员，HR 和普通员工没有 Dify 账号。
- [ ] 4.3 系统管理员不能用企业微信扫码登录 Frappe，只能用账号密码登录（建议开两步验证）；用系统管理员账号扫码时被拒绝。
- [ ] 4.4 通讯录同步确认覆盖全企业后，再打开 `full_directory_verified`；用一个测试账号实测：从企业微信删除后，Frappe 里的用户被停用。
- [ ] 4.5 服务器上 `deploy/secrets/` 权限为 600 / 700，仓库目录里没有密钥文件；日志里搜不到 Key、Token 和手机号。
- [ ] 4.6 Frappe 的 `encryption_key` 和备份私钥另存一份到服务器以外（离线保管）。
- [ ] 4.7 Claude 在服务器上做一次安全复查：端口暴露、管理后台来源限制、SSRF 代理只放行 X3/X4、容器日志脱敏。

## 5. 功能验收

### 5.1 自动测试（Claude）

- [ ] 5.1.1 在服务器上的测试站点跑 `tests/e2e` 全部用例通过（用合成数据，不连生产站点）；HR 助手对话用真实模型跑。
- [ ] 5.1.2 测完没有残留的 `E2E` 开头的合成数据。

### 5.2 真机验收（JQ 和试运行人员，用企业微信手机端）

每项用两个不同岗位的真人账号做。

- [ ] 5.2.1 问一个制度问题，回答带出处；换一个看不到该制度的岗位问，答不出这份制度的内容。
- [ ] 5.2.2 问“我的岗位职责”“我还有几天年假”，回答是本人的数据。
- [ ] 5.2.3 说“帮我查某某的假期”，助手不回答别人的数据。
- [ ] 5.2.4 发起请假：助手先起草，回复“确认请假”后才提交；上级收到审批卡片并通过，HR 收到卡片并通过，申请人看到结果。
- [ ] 5.2.5 上级在卡片上退回，申请人收到退回结果；卡片状态更新，重复点击不重复处理。
- [ ] 5.2.6 HR 新建一个员工档案，入职负责人收到待办，关掉自己的待办后任务完成。
- [ ] 5.2.7 HR 在 Wiki 发布一篇制度，几分钟内能在企业微信里问到；撤回后问不到。
- [ ] 5.2.8 HR 关掉某岗位的“查假期”开关，该岗位员工查假期时提示“没有开通”；打开后恢复。
- [ ] 5.2.9 回答里不出现手机号、身份证号、银行卡号、工资。
- [ ] 5.2.10 从提问到收到回复，常见问题不超过 8 秒（记录 10 次的耗时）。

## 6. 运维（GPT，Claude 复核）

- [ ] 6.1 每日备份定时任务开启，第二天检查生成了加密备份包，旧包按保留天数删除（`docs/manual/P3-每日备份.md`）。
- [ ] 6.2 用最近一个备份包恢复到新项目名，Frappe、Dify、X3/X4/X5 都能用，数据和原环境一致；记录停机时间和恢复用时。
- [ ] 6.3 发布和回滚：升级一次 X4 镜像再回滚，服务不中断或中断时间在手册写明的范围内（等 P3-G1 合入）。
- [ ] 6.4 监控告警：停掉一个服务，管理员在约定渠道收到告警；恢复后收到恢复通知（等 P2-G5 合入）。
- [ ] 6.5 管理员手册、部署运维手册定稿，运维照着手册能独立完成 6.1 – 6.3。

## 7. 试运行

- [ ] 7.1 按 1.6 的范围开放给试运行人员，发用户手册（`docs/manual/用户手册.md`）。
- [ ] 7.2 问题统一记录（时间、谁、问了什么、哪里不对），Claude 每周汇总分类，修复后回复。
- [ ] 7.2.1 每周一在服务器 `deploy/` 下跑 `make ai-report`（周报存在 `deploy/data/reports/`）：看用量、P95 耗时、费用、出错和兜底比例；被点踩、出错的回答按 ID 到 Dify 后台“日志”里看原文，归类后补进标准问题集（`tests/e2e/golden/`）。
- [ ] 7.3 试运行结束时达到：
  - 没有未修复的越权、敏感字段外泄或审批错单问题；
  - 制度问答抽查 20 个问题，答对且带出处的不少于 16 个；
  - 请假和入职流程都至少有 5 单完整走通；
  - 试运行期间没有丢数据，备份每天成功。
- [ ] 7.4 TensorZero 要不要上：Claude 根据试运行的模型用量和故障情况给出结论。同时根据周报决定要不要加 Langfuse（需要节点级追踪、按员工看费用时再上，要多约 4GB 内存）。
