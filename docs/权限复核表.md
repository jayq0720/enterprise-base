# 权限复核表（P2-C3）

列出每类人在平台里能看什么、能改什么、能审批什么。表里“现状”一栏写的是代码和配置现在实际怎么做。带 ★ 的地方 JQ 已于 2026-10-16 确认按默认做，结论见第 5 节。

更新：2026-10-16。依据：X3（`services/kb_gateway`）、X4（`services/frappe_mcp`）、X5（`services/policy_sync`）、`config/dify/hr-assistant.yml`、ADR 0001、任务卡 P1-G1。

## 1. 角色

| 角色 | 是谁 | 在哪里定义 |
| --- | --- | --- |
| 员工 | 在职员工，有企业微信账号 | Frappe Employee（状态 Active，`wecom_userid` 由 X2 同步） |
| 请假审批人 | 员工档案上的“请假审批人”，没有就用部门的 | Frappe HR（Employee.leave_approver / Department） |
| HR 专员 | 维护制度、员工档案、处理请假 | Frappe 角色 HR User（GPT 配置） |
| HR 管理员 | 发布制度、改审批规则、看全员数据 | Frappe 角色 HR Manager（GPT 配置） |
| 系统管理员 | 部署、录入模型 Key、配应用 | Frappe System Manager、Dify 管理员 |
| 集成账号 | X3、X4、X5 调 Frappe / Dify 用的接口账号，不是人 | Frappe 角色 `EB Integration`（X1）、Dify 知识库 API Key |

身份怎么认：员工在企业微信里说话时，平台只认企业微信 userid（`sys.user_id`），模型改不了。离职（不是 Active）或一个 userid 对应多个员工时，一律当作查不到人，什么都看不到。

## 2. 员工在企业微信里（HR 助手）

| 能做什么 | 范围 | 现状 |
| --- | --- | --- |
| 问制度 | 只在自己能看的知识空间里检索：全员可见 + 本部门可见 + 本岗位可见 | 已实现（X3） |
| 没配岗位的员工问制度 | 只看全员可见 | 已实现（X3） |
| 查假期余额 | 只查自己 | 已实现（X4） |
| 查请假进度 | 只查自己，不含已取消的 | 已实现（X4） |
| 查待我审批 | 只列审批人是自己、状态待审批的请假单，显示申请人姓名 | 已实现（X4） |
| 发起请假 | 只给自己请；先出草稿，本人回复“确认请假”才提交 | 已实现（X4） |
| 在企业微信里直接审批 | — | 未做，X2 审批卡片（GPT，P2） |
| 查岗位职责 | 计划只查自己岗位的 | 未做，等 X1 |

任何时候都不返回、也不交给模型：手机号、身份证号、银行卡号、薪资；审批人的邮箱也不返回。查询结果由工作流直接整理成文字回复，不进模型上下文。

## 3. 后台（Frappe / Dify）

| 操作 | 员工 | 请假审批人 | HR 专员 | HR 管理员 | 系统管理员 |
| --- | --- | --- | --- | --- | --- |
| 看自己的档案、假期 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 审批请假 | — | 自己负责的 | ✓ | ✓ | — |
| 看全员档案（不含敏感字段） | — | — | ✓ | ✓ | — |
| 看敏感字段（手机、身份证、银行卡、薪资） | 本人 | — | — | ✓ | — |
| 编辑制度草稿（Wiki） | — | — | ✓ | ✓ | — |
| 发布制度（同步到知识库） | — | — | — | ✓ | — |
| 改知识空间的可见范围 | — | — | — | ✓ | — |
| 录入模型 Key、配 Dify 应用 | — | — | — | — | ✓ |

后台权限由 GPT 在 Frappe 里配置（fixtures），P2 交付时按这张表逐项验收。

**Dify 账号只给系统管理员（JQ 2026-10-16 确认）。** 能编辑 Dify 应用的人能用 X3/X4 的服务 Token 以任何员工身份查数据，所以 Dify 工作空间不给 HR 专员、HR 管理员和员工开账号。HR 助手和制度问答的 Web App 要关掉，只走企业微信。见 `docs/安全审查报告.md` S1、S2。

## 4. 集成账号（不是人）

| 账号 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| X3 用 | 读 Employee 的部门、岗位；调 `knowledge_spaces()`；在 Dify 知识库检索 | 不读敏感字段，不写任何数据 |
| X5 用 | 读 Wiki 文档和空间；调 `knowledge_spaces()`；往 Dify 知识库写、删文档 | 不读员工数据 |
| X4 用 | 读 Employee（姓名、userid）、Leave Type、Leave Application；读假期余额；**新建请假单** | 不读敏感字段，不提交、不审批请假单 |

★ X4 的接口账号在 Frappe 里能给任何员工新建请假单，“只能给自己请”是 X4 代码保证的（身份来自签名令牌，草稿签名后不能改）。Frappe 本身做不到“接口账号只能替调用人建单”，除非每个员工各配一个 API Key，管理成本很高。

## 5. JQ 确认的结论（2026-10-16，全部按默认）

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 部门主管（请假审批人）能不能在助手里查下属的假期余额和请假记录？ | 不能，只看等自己审批的单 |
| 2 | HR 能不能在助手里查任意员工的假期？ | 不能，HR 去 Frappe 后台查，助手只查本人 |
| 3 | HR 专员能不能看敏感字段（手机、身份证、银行卡、薪资）？ | 不能，只有 HR 管理员和本人能看 |
| 4 | 制度发布要不要审核？谁起草、谁发布？ | 要审核：HR 专员起草，HR 管理员审核后发布 |
| 5 | 能不能替别人请假（比如主管替下属）？ | 不能，只给自己请 |
| 6 | 接受第 4 节的做法吗：X4 接口账号能建任何人的单，由 X4 代码限制只给本人建？ | 接受，并在 P3 安全审查里专门测这一项 |
| 7 | 员工离职当天就不能再用助手吗？ | 是，以 Frappe 里员工状态变为非 Active 为准 |
| 8 | 没配岗位的在职员工只看全员可见制度，可以吗？ | 可以 |

第 1、2、5、6、8 条现有代码已经是这样做的。第 3、4、7 条要在 Frappe 里配置，交 GPT 做进 fixtures，见 `docs/task-cards/P2-G-权限配置.md`。第 6 条在 P3 安全审查时专门测。
