# 部署运维手册

读者：JQ 和客户运维。命令从仓库根目录执行；示例部署位置 `/srv/enterprise-base`、用户 `enterprise-ops` 须替换为实际值。真实域名、密钥和客户资料只在客户环境配置。此文提供步骤，本次不登录服务器、安装定时任务或配置真实群机器人。截图统一标“待服务器截图”。

## 准备环境与首次启动

1. 准备 Linux amd64、4 核、16 GB 内存、至少 60 GB 可用磁盘；备份、构建和恢复副本另需空间。安装 Docker Engine ≥28、Compose ≥2.24、Git、make、uv 及 Python 3.12。
2. 使用专门运维用户和单一部署 checkout；该用户须能调用 Docker。保护账号、SSH 和服务器访问权限，不向普通员工开放 Docker 权限。
3. 从 `jayq0720/enterprise-base` 获取经 CI 和 Claude 审核、JQ 合并的 main 提交，记录完整 SHA；镜像和许可证以 [VERSIONS.md](../../deploy/VERSIONS.md) 及锁文件为准，不改成 latest。
4. 本机试用使用 localhost、HTTP、127.0.0.1。服务器在首次建站前确定最终域名，配置 dify/hr/wecom 三个子域 DNS、80/443 和管理员固定出口；不要建完真实站点再随意改 EB_DOMAIN，域名变化可能新建另一站点。
5. 执行下列初始化；首次下载/冷构建不计入本地“30分钟可登录”目标，ARM 仿真不承诺耗时。

```sh
cd /srv/enterprise-base
make -C deploy init
# 用本机安全编辑器修改 deploy/secrets/.env，禁止在终端打印内容。
make -C deploy verify
make -C deploy up
make -C deploy status
```

6. 真实配置只放 `deploy/secrets/`，目录及子目录 700、文件 600，属主为运维用户；仓库只提交 `.env.example`。环境值单行，不加引号、不做变量展开。发布会重写 secrets/.env：除切换的镜像摘要外，值保留，但注释和排版会丢失；配置说明另存客户私有运维文档，仍不得写密钥。
7. 本机浏览器打开 `http://dify.localhost/install` 建立 Dify 管理员；打开 `http://hr.localhost` 用 Administrator 和私有管理员密码登录，完成公司向导。服务器使用对应已确定的 HTTPS 域名，且来源须在管理员白名单中。
8. 本机初始化无法解析域名时按 [LOCAL.md](../../deploy/LOCAL.md) 配 hosts；远程仅回环环境通过安全 SSH 转发访问，不把本机监听误当公网入口。
9. 建立个人管理账号、双因素和 HR 角色；ERPNext 是 HRMS 依赖，保留安装，用 Module Profile 隐藏普通用户无需的模块。日常配置见[管理员手册](管理员手册.md)。

`make up` 重试时保留命名卷；不要运行 `down -v`。三套项目名分别为 `<EB_PROJECT>`、`<EB_PROJECT>-dify`、`<EB_PROJECT>-hr`。`deploy/data/` 和 `secrets/` 不进 Git，生成的配置可能含凭据，不上传、打印或作为 CI 附件。

## 配置企业微信和独立接口

1. 在企业微信自建应用后台设置可见范围、可信域名和服务器出口可信 IP；通讯录权限与应用 Secret 分开管理。
2. HR 预先建 Employee 并关联唯一 wecom_userid 和启用的 User。未知身份不自动创建账户，不能按姓名猜绑定。
3. 按[扫码登录](P1-企业微信扫码登录.md)和[通讯录同步](P1-企业微信通讯录同步.md)，在私有站点配置分别填写 `eb_wecom_login`、`eb_wecom_sync`。通过安全文件编辑录入，不把 Secret 放命令参数或历史记录。
4. 在 Frappe 启用 X3/X4/X5 各自技术账号并单独生成 API 凭据；X3/X5 仅 EB Integration，X4 仅 EB X4，不共用管理员 Key。
5. 在服务器 `.env` 录入这些凭据和 Dify 知识库 Key，执行 `make -C deploy policy-sync`、`make -C deploy hr-assistant`；首次基础建站不要求尚未生成的集成凭据。
6. 按[管理员手册](管理员手册.md)导入两个 DSL、配置模型、MCP、知识空间；关闭“HR 助手”和“制度问答”两个 Web App，保留 API，并从可达 Dify 的浏览器验证旧分享页不可继续对话。
7. 填好私有 DIFY_API_KEY 和 WECHATCOM* 配置后执行 `make -C deploy wechat`。默认 bridge 模式；企业微信回调为 HTTPS wecom 域名下的精确 `/wxcomapp`。
8. 卡片和签名回调、两级审批全部前置通过后，按[卡片部署步骤](P2-审批卡片部署与验收.md)切 approvals 并运行 `make -C deploy wecom-cards`；真实聊天、签名拒绝、重复点击、非指定审批人和离职拦截逐项联测后才上线。

上述 make 目标执行时会校验必填项并生成私有环境文件，不手改生成的 policy-sync/kb-gateway/frappe-mcp/dify.env。企业微信渠道上游会打印敏感内容，部署已丢弃该渠道原始日志；排查只取状态和脱敏错误类别，不临时打开完整请求日志。

## 上线必做：入口、身份和权限

1. 服务器对外绑定前设 `EB_SCHEME=https`、合适的 `EB_BIND`、`EB_ADMIN_ALLOW_CIDRS`；白名单只写管理员真实固定出口 IPv4/IPv6 CIDR，不写全网或 Docker 网桥网关。
2. 只有 EB_BIND 精确为 127.0.0.1 时，依靠回环端口隔离而不做 Caddy 来源匹配；其它绑定均限制 Dify/HR 全路径，包含 `/v1/*`、`/login` 和 REST。
3. 从白名单内外分别实测：内侧可登录，外侧 403；伪造 X-Forwarded-For 不改变结果。核对 Docker 转发后 Caddy 看到真实客户端 IPv4/IPv6；若变成网关，先修 Docker userland-proxy 或经评审改 host 网络，不放行共享网关。完整清单见 [ADMIN-ACCESS.md](../../deploy/ADMIN-ACCESS.md)。
4. 员工扫码路径尚未按独立入口方案开放时，不为扫码放开整个 HR 后台。企业微信消息入口仅公开必要回调，保留应用验签。
5. **System Manager 不能企业微信扫码登录**。个人管理账号使用密码和 OTP 双因素；在 System Settings 开总开关、选择 OTP App、关闭按受限 IP 绕过，同时在 Role → System Manager 开 Two Factor Authentication，再退出验证。
6. **只有 HR Manager 可以改主管审批人和 HR 审批人**；用 HR User 通过页面和 REST 修改均须拒绝，不能靠页面只读算验收。
7. 通讯录上线前，管理员确认 directory_secret 确实覆盖全企业、接口无分页缺失；先跑“缩小应用可见范围不会误离职”的反例，再在 `eb_wecom_sync` 设置 **`full_directory_verified: true`**。仅开启应用可见范围不等于取得完整目录授权。
8. 开启后实测停用一个合成离职人员：Employee 变 Left、User 禁用、旧会话失效；企业微信问助手收到“未找到你的在职员工信息”。错误、限权或分页不全时应整批失败，不能批量停用。
9. 核对两个 Web App 关闭、岗位/知识范围反例、敏感字段 REST/导出拒绝及 X4 提交/删除拒绝；用合成数据，不把员工信息发给模型或测试报告。
10. 在测试环境导出角色、字段、Workflow 等 fixtures 并空库回放；客户私有系统设置单独归档。不要只在线上手工改了就算完成。
11. 完成下面的备份、隔离恢复、发布失败与回滚演练以及告警验收，再由 JQ 确认上线。此前所有未执行项保持“待测”。

## 每日加密备份

1. JQ 在另一台可信机器使用官方 age 生成密钥，离线保存解密私钥；服务器只保存公钥。私钥不得放 `deploy/secrets/` 或备份源。
2. 联网机器按 `deploy/age.lock.json` 下载固定版官方包，核对包及 age/age-keygen/LICENSE 文件 SHA256；不修改锁文件绕过检查。
3. 把三个文件离线放到服务器 `deploy/data/tools/age-1.2.1/linux-amd64/`，目录和程序 700、LICENSE 600，属主为运维用户；执行 make verify 核对。
4. 服务器 `.env` 设置 EB_BACKUP_RECIPIENT、EB_BACKUP_DIR、EB_BACKUP_DAILY、EB_BACKUP_WEEKLY；默认目录 data/backups，最近7天加最近4周每周最新一份。外部目录用绝对路径，提前建成同一用户所有的700目录。
5. 在维护窗口执行 `make -C deploy backup`，健康检查短暂持锁时备份最多等待300秒；成功仅输出“备份:成功”；检查最新 `.tar.age` 非空且权限600。备份会暂停应用写入，恢复原先运行的服务并等待健康；耗时以客户数据实测为准。
6. 包含 Frappe 数据库/附件、全部非模板 PostgreSQL 库、Qdrant 全快照、Dify 文件和插件、Caddy 证书、已建企业微信会话卷及整个 secrets；清单在加密包内。
7. 成功且明文暂存清理后才删除本项目过期包。异地副本和挂载由 JQ 配置并验证，脚本不会自动完成异地传输；同盘包不能抵御整机损坏。
8. 每次大版本升级前及定期执行下节隔离恢复。备份生成成功和最近备份时间正常都不证明包能恢复。

### 安装每天北京时间03:00的定时器（服务器到位后由JQ执行）

先手动完成成功备份。替换下列路径和用户，用 `uv python find 3.12` 得到解释器绝对路径，替换 `/path/to/python3.12`。确保该用户 PATH 可调用 Docker/uv/Git。以下不包含任何密钥。

`/etc/systemd/system/enterprise-backup.service`：

```ini
[Unit]
Description=Enterprise encrypted backup
After=docker.service
Requires=docker.service
[Service]
Type=oneshot
User=enterprise-ops
WorkingDirectory=/srv/enterprise-base/deploy
Environment=PATH=/home/enterprise-ops/.local/bin:/usr/local/bin:/usr/bin:/bin
ExecStart=/path/to/python3.12 backup.py secrets/.env
UMask=0077
KillMode=process
TimeoutStartSec=infinity
TimeoutStopSec=infinity
```

`/etc/systemd/system/enterprise-backup.timer`：

```ini
[Unit]
Description=Daily enterprise backup
[Timer]
OnCalendar=*-*-* 03:00:00 Asia/Shanghai
Persistent=true
Unit=enterprise-backup.service
[Install]
WantedBy=timers.target
```

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now enterprise-backup.timer
systemctl list-timers enterprise-backup.timer
```

Persistent 会补跑错过的任务，补跑同样暂停应用。取消执行用 `sudo systemctl stop enterprise-backup.service` 并等恢复完成。不要强杀；SIGTERM/SIGINT 延迟到安全边界。断电/SIGKILL 后先确认无操作进程、服务恢复，再人工清理 `.backup-clear-*` 明文残留。失败摘要只含步骤/错误类型。

## 在新项目恢复备份

1. 准备备份完整40位代码提交、原精确镜像 ID、固定 age 工具和足够空间；不要用同标签的新镜像替代旧镜像。
2. JQ 临时挂载离线私钥为运维用户所有的600文件，备份包同样600；不把私钥复制到服务器 secrets 或业务卷。
3. 指定未使用的新项目名和回环端口，执行下列命令。重复尝试换新项目，不覆盖原环境或失败半成品。

```sh
make -C deploy restore BACKUP=/srv/backups/example.tar.age IDENTITY=/media/offline/identity.txt RESTORE_PROJECT=eb-restore RESTORE_PORT=18080
```

4. 核对副本 `deploy/data/restore-result.json` state=ready，容器健康及两个 HTTP 检查通过。前端采用恢复域名，Frappe站点目录仍是原名；访问方法见[完整恢复](P3-完整恢复.md)。
5. 核对记录数、附件 SHA256、Dify 工作流/插件、Qdrant 集合/别名和检索；记录开始/结束时间及耗时，由 Claude 完成云端整套验收。
6. 恢复保留目标新数据库名/密码，仅拷 Frappe 解密密钥；Caddy及企业微信会话一并恢复。副本的队列、调度、邮件、企业微信和 X3/X4/X5 保持关闭，不直接 make up 或接正式入口。
7. 失败时保持副本停服，检查 stop_failed 摘要；宿主解密暂存与容器临时输入会清理，私有副本和业务卷留在客户本机。结束取走离线介质，不上传副本配置或 dump。

`make restore` 始终是隔离演练，不提供原环境覆盖参数。发布后的原项目回退必须走下节受确认保护的 rollback。副本激活属于另行评审的正式切换，不能把通知关闭导致的卡片测试失败当作卡片已验收。

## 发布与回滚

发布与回滚入口已合入 main；使用已审核且 CI 通过的版本。首次引入该入口前须按同一 main SHA 构建并验收 Frappe 基线镜像，带正确 revision 标签；没有可信基线时入口会拒绝。

1. 在独立测试项目验证目标 main 提交、固定镜像和升级结果，包含故意失败与回滚演练；生产安排维护窗口并通知业务负责人。每次发布都会执行完整 make build，包含底座镜像；缓存丢失或首次构建需联网，可能耗时几十分钟、另需约15 GB构建空间，再加备份暂存和数据卷空间。发布前核对各分区余量及 docker system df；不要随手执行 docker builder prune 清掉构建缓存。
2. 检查部署 checkout 干净、origin 指向本仓库，保存当前完整 SHA；不先切目标版本、不手改镜像、不重跑会改摘要的 make init。
3. 用目标 main 的完整40位 SHA 发布；入口持操作锁，先检查、验证目标、备份，独立保存发布前加密包与状态，再切代码。

```sh
make -C deploy release REVISION='替换为目标main完整40位SHA'
```

4. 执行顺序为停入口/应用写入 → Frappe配置/迁移/启动 → Dify → X3/X4/X5 → 企业微信入口 → 容器及HTTP自检；原未开启的可选服务不擅自开启。数据库/队列引擎升级另作方案。
5. 成功记录 ready；失败查看步骤与状态，保留发布目录和原镜像。失败不会自动丢弃数据库恢复信息，也不自动执行有数据丢失风险的回滚。“准备镜像”失败时，代码和.env可能已经是目标版本，服务仍是旧版本；先暂停自动发布，指定当次 RELEASE_RECORD 执行 make rollback，按记录提示决定是否补 RESTORE_DATA/IDENTITY，再重试发布。不能凭服务仍可访问就当作发布成功，也不要手动改回代码/.env跳过记录。
6. 不涉及迁移的发布可先运行 `make -C deploy rollback`；省略 RELEASE_RECORD 时取最近未回滚记录。迁移一旦开始便要求恢复发布前数据，不推断“这次迁移可能没改表”。
7. 数据恢复必须显式 RESTORE_DATA=1、提供离线私钥，并在交互终端两次输入项目名与“确认丢失发布后数据”；没有免确认参数。回退点是发布前备份，备份完成后的新增和修改都可能丢失，包括镜像准备期间的业务写入。确认前核对回退点和业务窗口内新增记录，必要时另外加密保存当前状态供人工核对，不能把它自动合回旧库。

```sh
make -C deploy rollback RELEASE_RECORD='/srv/enterprise-base/deploy/data/releases/替换为发布记录/release.json' RESTORE_DATA=1 IDENTITY=/media/offline/identity.txt
```

8. 回滚会丢失发布后新增/修改的数据，恢复 PostgreSQL、Qdrant、文件卷及Frappe数据库；保留目标数据库凭据，只导入解密密钥，再启动原版本并自检。
9. 配置、密钥或项目在发布后变化时会拒绝自动回滚，交运维审查；不改状态文件绕过。数据库恢复失败可能留下空库，保持应用停服、原发布记录及加密包；修复原因后用同一 RELEASE_RECORD 和备份再次执行，重新预检及二次确认，不另建发布记录、不自动重试或接回流量。
10. 验收记录版本、镜像摘要、失败步骤、恢复点及数据核对结果；发布记录虽不存密钥，仍按私有运维资料保管。加密发布前包独立于每日保留策略，不随日常清理删除。

### 发布记录与旧镜像保留

发布前的 data/releases/<记录>/before.tar.age 是每次独立留下的完整备份，release-cache 标签也不自动清理，均不受每日备份保留策略控制。默认至少保留最近3次发布，以及所有未完成、失败待处理或仍需回退的记录；这些额外记录可能使总数超过3次。

在无备份/恢复/发布执行的维护窗口暂停自动发布，先列出待删记录及其镜像标签，与保留记录的 running_images 和当前容器逐一核对。确认不再需要该恢复点、必要的离线归档已包含代码和精确镜像后，才手工删除对应旧记录目录及仅属于这些记录的 release-cache 标签。共享镜像、当前镜像和仍被保留记录引用的标签不能删，不批量执行 image/system prune、删除卷或按镜像ID强删。清理后核对最近3次完整包和所需镜像仍在。

## 监控与告警

make health 已合入；先手动运行一次并逐项核对结果。只在正式活动环境装定时器，隔离恢复副本故意关闭调度器，不能按活动环境验收。

1. 私有 `.env` 填 EB_HEALTH_PROFILES，按已启用功能列 `wechat,policy-sync,hr-assistant`；未填时仍检查已存在的可选服务，填后还能发现整组容器被删。
2. 阈值按 `.env.example` 的 EB_HEALTH_* 配置：卷空间15%、MemAvailable10%、备份26小时、队列100、证书14天、HTTP超时10秒。备份按加密包名UTC时间，不按复制后的mtime。
3. 在服务器私有 `.env` 填 EB_ALERT_WECOM_WEBHOOK，使用HTTPS群机器人地址，文件600；不要把地址放systemd、命令参数、PR或聊天。留空只写本机日志，检查失败也正常结束；格式错误或私有文件权限错误会非零退出。
4. 执行 `make -C deploy health`，核对每项通过/失败及数值；维护锁被备份/恢复/发布占用时跳过该轮，不发送误报或恢复消息。
5. 检查三套容器、内部登录页/X3/X4/X5健康接口、实际命名卷分区、Linux可用内存、备份时效、调度启用与真实进程锁、三条队列积压、HTTPS证书链/域名/到期时间。无原生healthcheck的服务检查运行状态。
6. 内部HTTP探针避开管理员公网白名单，只返回状态码；进程/HTTP健康不证明模型Key、制度权限或企业微信可用，入口外部验收仍按“上线必做”。
7. 首次故障通知一次，持续每小时最多一次尝试；恢复发“已恢复”。投递超时也限频，失败仅记异常类别，不输出机器人响应；状态600保存在 data/health-state.json，不删除状态来重复试告警。
8. 测试环境停一个容器、临时提高磁盘阈值，各执行一次 health；一小时内重复应不刷屏，恢复容器/阈值后各收到一次恢复。另测空Webhook正常结束。实际机器人收发由JQ服务器验收，CI只用模拟HTTP。

### 每5分钟检查（服务器到位后由JQ执行）

先手动跑通。创建 `/etc/systemd/system/enterprise-health.service`，Unit、用户、目录、PATH 和 UMask 与上面的 backup service 相同，把 Description 改为 `Enterprise health check`，ExecStart 改为 `/path/to/python3.12 health.py secrets/.env`。保留安全退出时间，不设置含密钥的 Environment。

`/etc/systemd/system/enterprise-health.timer`：

```ini
[Unit]
Description=Enterprise health every five minutes
[Timer]
OnBootSec=2min
OnUnitActiveSec=5min
Unit=enterprise-health.service
[Install]
WantedBy=timers.target
```

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now enterprise-health.timer
systemctl list-timers enterprise-health.timer
```

先用 `systemctl status enterprise-health.service` 核对退出状态；输出仅有状态和数值，投递失败不会泄露Webhook。没配机器人时依靠本机日志，不把exit=0当成业务全健康；以逐项结果为准。当前开发不安装这些单元。

## 测试环境自动发布（已实现，默认关闭）

1. main 已有 deploy-test 流水线和 SSH 强制命令；先完成从零部署及一次手动发布/回滚，再按[测试环境自动部署](../测试环境自动部署.md)开启，不把当前“跳过”状态当作部署成功。
2. 服务器安装仓库外的强制命令脚本，在专用authorized_keys设置restrict和command，只接受40位提交号。GitHub的test环境仅配置专用SSH部署私钥、已人工核对的服务器指纹和登录地址；业务/模型/数据库密钥仍只在服务器私有文件。私钥录入GitHub后按该说明删除服务器生成副本，不把部署私钥、指纹原文或登录地址发到PR/聊天。
3. JQ完成配置和验收后，设置仓库变量 EB_TEST_DEPLOY=true；关闭时清除该值或撤销专用公钥。只认本仓库main的push触发且成功的ci；服务镜像还需service-images完成、固定摘要进main才会更新，不能只改源码就认为X3/X4/X5已更新。
4. 服务器从当前部署checkout执行make release，由入口负责备份和切换；不要先git pull或checkout目标版本。同一环境串行，不取消在途备份/迁移；部署完成以release自检为准，不能只看make health退出0或Git提交。
5. 已复核一个待修边界：当前强制命令仅凭HEAD相同就跳过；镜像准备失败后HEAD可能已是目标、服务仍旧。此时重跑流水线可能错误跳过，先按当次记录手动rollback再重试。启用前请Claude按[#113复核意见](https://github.com/jayq0720/enterprise-base/pull/113#issuecomment-6495027271)补成功发布状态及运行版本/健康校验，并补同提交失败重跑反例；修复和服务器联调完成前保持默认关闭。
6. 自动部署不做数据库回滚；回退仍要离线私钥和人工二次确认。正式环境继续手动发布。服务器须能访问GitHub/GHCR，SSH访问范围按部署说明配置并复核。
7. 验收“合入main→ci通过→测试环境更新”，以及非法提交号/注入拒绝、真正成功提交的幂等跳过、构建失败后重跑拒绝；只记录去标识状态。定时备份、每5分钟健康检查、企业微信应用/回调分别验收，截图均待服务器补充。

## 密钥轮换和配置留档

1. 先备份，在测试环境演练替换，约定短维护窗口；按凭据用途建立私有清单，禁止在共享记录写值。
2. Frappe API Key/Secret 在对应独立技术User重建，更新服务器 `.env` 后重新生成并重建对应服务；核对旧凭据失败、新凭据和权限反例通过。
3. X3/X4/X5服务Token与Dify环境变量、MCP授权同时更新；MCP重新“授权→更新”。X4会话签名密钥轮换使旧会话/草稿失效，员工须重新起草。
4. Dify应用Key轮换同时更新DIFY_API_KEY并重建wechat；知识库Key更新X3/X5各自配置。先确认新配置生效，再撤销旧Key。
5. 企业微信应用Secret在聊天、eb_wecom_login、eb_wecom_sync、eb_wecom_cards一致更新；Token/AESKey与企业微信回调设置同步，重新执行检查/重建并GET验签，再联测聊天和卡片。
6. Frappe加密密钥、Dify SECRET_KEY 和数据库密码不能当普通Token直接替换：会影响已存加密凭据或数据库访问，须单独设计原生迁移、备份和恢复方案，未经验证不改值。
7. age公钥轮换只影响新包；保留旧包对应的离线私钥到所有相关备份/发布包到期，定期演练解密。私钥不进入日常服务器备份。
8. 共享字段/角色/工作流配置导出fixtures、PR评审及空库复现；客户数据和秘密保持客户私有。每次升级复核版本表、许可证和遥测设置。

## 常见故障与交接

| 现象 | 先检查与处理 |
| --- | --- |
| 本机后台403 | 是否精确回环绑定并重新生成/重建Caddy；不要加网桥网关白名单 |
| 对外后台全部403 | 核对真实出口CIDR和Docker转发后的连接来源，按IPv4/IPv6分别验证 |
| 插件/worker启动失败 | 用版本表核对Debian Nginx、全局WARNING及plugin_daemon单独WARN，不全局改WARN |
| HR助手系统不可用 | Frappe字段/迁移是否先完成、岗位是否真实、X4固定摘要及MCP授权更新；再看去标识状态码 |
| 制度未更新 | Workflow是否发布、X5健康、Webhook签名及知识库ID/索引；不导出原始Webhook请求 |
| 入职没出待办 | 招聘前置、模板冲突、活动负责人、入职窗口及HR Manager保存；不创建虚假招聘记录 |
| 卡片收不到/未更新 | 是否approvals模式、可信IP、回调验签、当前审批人及卡片状态；不反复重发造成重复 |
| health提示维护中 | 等当前备份/发布完成，不删 operations.lock 文件；删文件可能产生第二把锁 |
| 备份/恢复失败 | 只取步骤和异常类型，核对暂停服务已恢复或副本已停；不要删原卷或改备份清单 |
| 定时任务未运行 | 检查timer下一次时间、用户PATH/权限及service退出状态；手动测试后再启定时 |

交接只记录北京时间、环境代号、代码/镜像摘要、状态数量、恢复耗时和去标识错误类别。禁止转发完整Compose config、docker inspect、数据库dump、员工正文、Cookie、Key、Token、回调查询串或客户私有配置。CI成功不替代模型、企业微信、白名单、离职和整套发布/恢复的客户验收。
