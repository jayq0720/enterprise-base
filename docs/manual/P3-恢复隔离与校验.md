# 恢复隔离与校验（P3-G2）

`deploy/restore_guard.py` 提供恢复前置模块；当前尚无 `make restore`，不能把校验通过当成组件已恢复。后续入口依次接入原生数据恢复、Caddy/企业微信卷恢复及正式覆盖的显式参数和二次确认；本模块一律拒绝已有项目，不提供覆盖入口。

`prepared` 和备份共用操作锁及延迟取消机制，先验证备份包、解密私钥文件的私有权限，再使用真实 age 解密、校验全部 SHA256。随后检查各组件负载和索引完整；原包包含企业微信容器时必须同时有会话归档，Caddy 证书和每个数据库包也不可缺少。解密内容只放 `deploy/data/` 同分区的 700 临时目录，结束或调用方失败时清理。

新项目名不能与来源项目的三套 Compose 名称交叉重叠；目标目录必须不存在且不经过符号链接。只读检查 Docker 容器、卷和网络，拒绝已有标签或名称前缀匹配的资源，包括手工建立而没有 Compose 标签的卷。此步骤不停止、删除或修改任何 Docker 资源。真正初始化环境前和操作锁持有期间，调用方仍须禁止并发维护或手工创建同名资源。

Frappe 外层归档在写文件前检查编号、全站四类文件、路径、数量、重复项及文件类型，拒绝穿越、绝对路径和链接；只输出 700 目录、600 文件。公开/私有附件的内层 tar 留给后续原生 bench 恢复，不在宿主机展开。`site_settings` 仅从源站点导入 `encryption_key` 和 `backup_encryption_key`，数据库名、口令、主机及其它配置保留目标值；验收前暂停调度、邮件和企业微信卡片，源配置中的回调或其它字段不会导入。

`make -C deploy verify` 纳入五项测试：新项目隔离（Docker 替身）、密钥白名单、完整负载检查、原生外层 tar 拒绝反例，以及真实 age 解密和篡改拒绝。调用方失败也会清理明文；篡改包在查询 Docker 前被拒绝。尚未执行整套 Docker 恢复、正式覆盖或企业微信联测，耗时仍以 [真实 Frappe 恢复演练](P3-Frappe恢复演练.md) 的既有 CI 基线为准；Dify/Qdrant 整套恢复须由 Claude 云端演练补录。
