# 恢复目录准备（P3-G2）

`deploy/restore_workspace.py` 为统一恢复入口准备新项目目录，本身不创建或启动 Docker 业务资源。须在 `restore_guard.prepared` 完成包校验、新项目检查并持锁后调用；统一入口见[完整恢复](P3-完整恢复.md)，正式覆盖确认仍待接入。

先在本机备好备份中的精确镜像 ID 和代码提交。Frappe 自建镜像要提前另存离线镜像包（`docker image save`），恢复机器上用 `docker image load` 导入；不能仅重建同名 tag 后当作原镜像。准备过程只检查，不自动拉取或替换镜像。离线环境还需按每日备份手册准备 age，并保存固定上游源码缓存。

恢复目录限制在当前仓库忽略的 `deploy/data/restores/` 内，使用备份提交创建独立、detached 的 Git worktree，代码和版本表保持原版。目录 700，复制的密钥文件和生成的 JSON 配置为 600；保留 Dify 等组件的数据解密凭据与二进制配置，重新生成目标 MariaDB root、PostgreSQL 和 Frappe 管理员口令。不导入旧站点数据库名或密码，后续仍由原生站点恢复程序建立独立数据库。

入口统一改为本机 HTTP、新项目 `.localhost` 域名和调用方指定的非特权空闲端口，关闭 HTTPS 入口与自动重启；恢复副本的企业微信回调采用 bridge，不能当作正式回调环境。Frappe 保留源站点目录名，前端正确映射主站点；原主站点提示保存到 `.env`，让后续再备份仍可识别多站点，多站点无法确定主站时拒绝。共享文件卷的所有使用者均设置 `nocopy`，站点 assets 卷保留镜像初始内容。Compose 生成时屏蔽宿主机同名环境变量，避免生产项目名或密码覆盖恢复配置。

生成的 `data/restore-edge.json`、`restore-dify.json`、`restore-hr.json` 供后续统一入口使用；包含内联凭据，不可上传、贴日志或 PR。不要在恢复 worktree 直接运行普通 `make up`，它会使用原版部署入口和默认端口。失败会删除本次已取得所有权的新目录，原目录不动；清理失败会明确报错，运维需检查残留。

测试实际创建/移除临时 Git worktree、运行原生 Compose 配置解析，核对口令隔离、文件权限、二进制复制、端口占用拒绝及失败清理。镜像清单与 prepare 使用协议替身，不代表整套 Dify/Frappe 已部署。真实整套恢复仍由 Claude 云端补测，截图待补。没有新增依赖，也不改上游源码或 `.github/`。
