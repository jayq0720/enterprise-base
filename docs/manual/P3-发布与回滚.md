# 发布与回滚

本流程只供部署管理员在维护窗口手动执行。每个部署使用一个checkout；备份、恢复、发布、回滚共享操作锁，期间不能另开终端运行make up、建站或手工迁移。数据库、Redis和Qdrant镜像升级不在本应用发布流程里，须先单独演练。源码工作区须干净，当前运行App镜像的revision标签必须与当前checkout一致，三项服务须匹配当前main锁定摘要；已有无标签部署不能猜基线或补假标签，应先在测试环境按真实版本重建验证。

## 发布

1. 确认当前checkout就是正在运行的基线版本，不先手工checkout新版本。
2. 确认所有运行密钥只在本机secrets/.env，权限600；配置每日加密备份、公钥及足够磁盘。离线私钥不留服务器。
3. 取得已经合入main的新提交完整40位SHA；新版本的服务镜像必须已写进main锁定配置。
4. 在部署仓库执行：

```sh
make -C deploy release REVISION=<新main完整40位SHA>
```

入口刷新main、独立校验目标、备份、另存专用回滚包和版本记录，再构建/解析新镜像。镜像准备失败不停止旧服务；切换开始后先停入口和应用，Frappe迁移完成后启动Dify及X3/X4/X5，再恢复原先启用的企业微信入口并自检。未启用的可选服务保持关闭。

状态在deploy/data/releases/<记录>/release.json，文件600，不含展开的环境变量。before.tar.age是独立加密包，不会随每日保留策略删除。旧镜像留本机release-cache标签，不在回滚窗口清理这些镜像、记录、备份或卷。不要打印完整Compose配置、Docker inspect、原始消息日志或服务器密钥。

## 失败和回滚

发布失败立即停止后续步骤并非零退出。先读固定步骤/错误类型和本次记录phase；不要直接启动旧代码去读已经迁移的数据库。构建准备阶段失败时，旧服务仍运行，但checkout/镜像配置可能已更新，应通过记录回退后再重试。

默认选择最新未回滚记录：

```sh
make -C deploy rollback
```

本实现正常发布总会执行全站迁移，因此其回滚必须恢复发布前数据。只有尚未进入迁移的失败记录可以只回退代码和镜像。需恢复数据时，先把离线私钥以本人所有、600权限挂载到本机，再执行：

```sh
make -C deploy rollback RESTORE_DATA=1 IDENTITY=/media/offline/identity.txt
```

操作者会看到“将丢失发布后产生的数据”，须在交互终端两次输入目标项目和固定确认语句，管道/自动yes不支持。先检查记录、备份摘要和解密，再停止应用、恢复数据库/文件/向量快照，清空过期队列缓存，切回旧提交和精确镜像并自检。已有站点连接账号及密码保留目标值，仅复制解密密钥。指定记录用RELEASE_RECORD=/绝对路径/记录/release.json，只接受当前部署data/releases内的记录。

密钥或部署配置发生变化时拒绝自动套用旧记录，需单独安排恢复；不要修改指纹、清单或容器标签绕过检查。恢复失败保持应用关闭并记rollback-failed，修复原因后重新恢复完整备份，不能把半成品当成功。结束后取走离线私钥介质。

## 验收与重新开放

核对代码提交、实际镜像、登录页、员工/岗位/请假记录数、附件SHA256、Dify应用/知识库和Qdrant检索。数据会倒退，须重新复核离职人员停用、账号角色与权限，验证企业微信及X3/X4/X5；外部发送结果不会随数据库倒退，审批卡片须另外核对。至少演练一次不存在镜像摘要导致准备失败，以及一次迁移后数据库回滚，记录开始结束时间、通过/失败和数据对照，不贴密钥或个人内容。

本机/CI的Git、锁、状态和协议测试不能替代整套云端发布回滚。Frappe和PostgreSQL原生组件分别有恢复测试，整套发布耗时及服务器截图待Claude云端演练后补录。截图位置：待服务器截图。

数据库覆盖中途失败时可能留下空库：保持应用停服、保留本次发布记录和原加密包，修复原因后用相同 RELEASE_RECORD、RESTORE_DATA=1、IDENTITY 重新回滚。重试重新校验备份并二次确认，不另建发布记录、不自动重试。控制器测试覆盖先失败、同记录同备份再次确认后成功。
