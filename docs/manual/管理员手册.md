# 管理员手册

读者：HR、HR 负责人和 IT 管理员。员工操作见[用户手册](用户手册.md)，服务器操作见[部署运维手册](部署运维手册.md)。本书按仓库固定版本编写；截图均待服务器补充，客户环境的企业微信、模型和浏览器操作仍须实测。

## 先分配账号和职责

| 使用者 | 账号角色和边界 |
| --- | --- |
| 普通员工 | Employee，关联本人 Employee 档案；查看本人资料、本人请假和获分配待办 |
| HR 经办人 | HR User，可维护常规档案、起草制度；看不到他人的敏感字段，不能改审批人、身份绑定或知识范围 |
| HR 负责人 | HR Manager，按工作需要兼任 HR User；维护敏感资料、审批人、知识范围、岗位开关、入职模板和制度发布 |
| 主管 | Employee + Leave Approver，只能办理当前指定给自己的审批，不得自批 |
| 系统管理员 | System Manager，部署配置和账号管理；不能用企业微信扫码登录，必须使用密码及双因素认证 |
| 接口账号 | X3/X5 使用 EB Integration，X4 使用 EB X4；不得授予管理员或 HR 角色 |

1. IT 从 Frappe 顶部搜索进入 User（用户），新建或打开指定用户。
2. 只勾选所需角色，保存；勿为方便而给所有 HR 授予 System Manager。
3. HR Manager 打开 Employee（员工），将 User ID 绑定到本人启用的用户，将“企业微信 userid”绑定到核对过的唯一身份。
4. 检查公司、部门、真实岗位和 Active 状态；没有岗位的员工不能使用四类 HR 助手工具，不批量填虚构岗位。
5. 普通员工只读本人手机号、证件、银行卡等敏感字段；HR Manager 可读写。HR User 即使兼任 Employee，也不能读他人的这些字段。
6. 用合成账号复核页面、REST 和导出；不得靠隐藏页面来代替权限。普通员工不授予 Employee 通用导出权限，接口账号不能导出员工资料。
7. HRMS 依赖 ERPNext，保留安装。IT 搜索 Module Profile（模块配置），在 Block Modules 隐藏普通用户无需的财务、销售等模块，再在 User 选择该 Module Profile；角色同时保持最小授权。隐藏模块不替代服务端权限。

IT 先在测试环境配置管理员双因素，再推广到正式环境：

1. System Settings（系统设置）开启 **Enable Two Factor Auth**，方法选 **OTP App**；关闭按受限 IP 绕过双因素的选项，保存。
2. Role（角色）打开 **System Manager**，勾选 **Two Factor Authentication**，保存。固定版本还会检查角色开关，仅开启系统总开关不够。
3. 使用个人管理账号退出重登，核对必须经过密码及验证码；按提示绑定认证器，先演练丢失认证器的原生重置流程，由 JQ 离线保管恢复材料，不截图二维码或验证码。
4. 把去密钥的系统及角色配置按原生 fixtures 归档到客户私有配置仓库，评审并在空库重放；共享 App 的默认导出仅覆盖约定的 EB 配置，不自动包含这些客户设置。OTP 秘密不进入 fixtures。

内置 Administrator 仅作受控应急账号，日常用个人 System Manager 账号，不用扫码登录兜底。

## 建立员工档案并导入组织任职

1. HR 先在后台建立真实 Employee 档案，填齐工号、姓名、性别、出生日期、公司及原生必填项；Excel 不负责新建员工，不填写虚构值。
2. 下载[组织与岗位导入模板.xlsx](../../config/frappe/imports/组织与岗位导入模板.xlsx)，阅读“说明”页，删除三张业务表中的合成示例行，保留表名、列名和格式。
3. 在“部门”表填写名称及上级；引用已有部门时填完整名称，包括公司缩写。
4. 在“岗位”表填写名称、多行岗位职责和额外可见知识空间；空间必须已建，填 EB Knowledge Space 完整名称，多个用英文逗号分隔。
5. 在“员工任职”表填写工号、姓名、企业微信 userid、部门、岗位、直属上级工号、入职日期这七列。工号和 userid 用文本格式，日期用 Excel 日期。
6. 不增加手机号、证件、银行卡、薪资或审批人列，不把这些内容塞进职责等单元格。
7. 用 HR Manager（新建岗位还需 HR User）或 System Manager 打开 `/app/eb-org-import`，选择对应公司，点“上传 xlsx”，保持文件私有。
8. 点“预检”，按表、行、列修正错误后重新上传；工号缺失、重复、姓名不一致或循环引用都会拒绝整批。
9. 核对数量和变更后点“整批保存”。保存会重新校验，失败整批回滚；重复导入更新已有记录，不增加重复员工。
10. 抽查部门层级、岗位职责和任职关系，再请测试员工通过助手查询本人职责。上传后按客户私有资料保管文件，不作为代码或 PR 附件。

注意空值的含义：userid 和入职日期留空保留原值；上级部门、额外知识空间、直属上级留空会清空。职责不可空。System Manager 若不兼任 HR Manager，不能借导入修改身份绑定或知识授权。Excel 的直属上级不是请假审批人，审批人另行配置。

## 维护岗位职责、知识空间和助手开关

1. HR 打开 Designation（岗位），按实际职责填写“岗位职责”，保存；不在职责中记录个人敏感信息。
2. HR Manager 在 Wiki Space 建立空间，在 Dify 建立对应知识库；知识库模型和索引由 IT 配置。
3. HR Manager 打开 EB Knowledge Space（知识空间），填写名称、Wiki 空间和 Dify 知识库 ID。一个 Wiki Space 只能绑定一次。
4. 全员制度勾“全员可见”；限定部门内容在“可见部门”选择完整部门名。
5. 岗位额外授权在 Designation 的“可见的知识空间”选择。只有 HR Manager（及内置 Administrator）可以改变可见范围，普通 HR 和普通 System Manager 不能修改。
6. Wiki Space 若配置原生角色权限，由管理员把 EB Integration 加入 Read 列表，不授予 Write 或 Wiki Manager，也不为同步而把受限空间改为开放。
7. 范围变化后等待 X5 对账并检查测试身份的检索结果；全员、部门和岗位授权取并集，不能只取消一种授权就认为已彻底撤权。
8. 要更换知识库或删除绑定，先取消全员、部门和岗位的全部授权，完成对账并确认旧库文档撤下，再变更绑定；不要直接删绑定。

在 Designation 的“企业微信助手”分节，HR Manager 按业务需要维护以下开关：

| 字段 | 效果 |
| --- | --- |
| 助手可查假期和请假记录 | 本人余额及本人请假记录 |
| 助手可发起请假 | 起草与确认请假 |
| 助手可查待我审批 | 当前分给自己的待审批单 |
| 助手可查岗位职责 | 本人岗位职责 |

四项默认开启，明确关闭的值在重复迁移后保留。HR User 不能改开关。关闭“发起请假”后，关闭前的草稿也不能继续确认；员工须在重新开通后重新发起。开关不能扩大员工身份和审批权限。先部署 Frappe 字段/权限，再升级 X4，最后逐项测试关闭、恢复和确认拒绝。

## 配置请假及两级审批

1. HR 按原生 HRMS 配置 Leave Type、Holiday List、Leave Period 和 Leave Allocation，给合成员工建立可用余额；不同类型的假期规则按客户确认设置。
2. HR Manager 打开 Employee，选择 `leave_approver`（主管审批人）和 `eb_hr_approver`（HR 审批人），保存。**HR User 不得修改这两个审批人**。
3. 主管必须在职、账号启用并有 Leave Approver；HR 审批人必须在职、账号启用且有 HR User 或 HR Manager。二者必须不同，也不能是申请人。
4. 没有单独主管时采用部门第一位请假审批人，部门审批配置也由 HR Manager 管理。不要把 reports_to 或 Excel 直属上级当成审批链配置。
5. 用测试员工起单，核对进入 `EB Leave Manager`；主管通过后进入 `EB Leave HR`，仍是 Open，余额尚未扣减。
6. 指定 HR 最终通过才成为 Approved 并扣减余额；拒绝不扣余额，退回后由员工修改再重送。
7. 需要取消已批准请假时，由原指定 HR 走原生取消流程，核对余额冲销，不直接改数据库状态。
8. 审批人随新单固定；修改档案不会重写老单审批链。HR 审批人缺失或与主管重复时补齐档案后重新起单，不伪造中间审批状态。
9. X4 接口账号只能新建草稿和受限读取，不能提交、审批、修改或删除。企业微信卡片上线前由运维完成签名回调与反例联测。

## 配置入职模板并生成待办

1. HR Manager 打开 Employee Onboarding Template，复制 `EB Synthetic Onboarding` 后改名，填写真实公司、岗位和可选部门。
2. 同一公司、岗位、匹配部门只保留一套模板；仓库合成模板不直接绑定客户公司。
3. 每项活动指定明确的启用 User 负责人，清空 Role；填写开始偏移、时长、说明及权重，关闭 `required_for_employee_creation`，避免建档与任务互相等待。
4. HR 先建立真实 Job Applicant，并准备唯一、同公司、同岗位、已提交的 Job Offer；不要用占位招聘记录绕过原生前置。
5. 在 Employee 关联该应聘者，填真实入职日期、假日表、公司和岗位，再由 HR Manager 保存。
6. 核对自动生成并提交的 Employee Onboarding，以及关联的 Project、Task 和负责人 ToDo；重复保存不应重复生成。
7. 缺招聘记录、模板冲突或负责人无效时，档案保留但不生成待办；按提示补齐后由 HR Manager 再保存重试。HR User 保存不能自动提交入职单。
8. 默认自动处理最近 30 天入职人员；更早入职按原生手工入职流程办理，需要调整窗口时交 IT 配置，不更改真实入职日期。
9. 负责人完成后关闭自己的 ToDo，任务随之完成，全部任务完成后入职单完成；其他人代关 ToDo 不算负责人办结。

## 起草、审核并发布制度

本项目采用原生 Workflow `EB Wiki Review`，保留提交、退回和发布轨迹，并由 App 再校验发布标记，避免直接修改标记绕过审批。

1. HR User 在 Wiki Document 新建或修改制度草稿，选择正确 Wiki 空间，保存为 `EB Draft`。
2. 自查正文不含人员、手机号、证件、银行卡或薪资，使用动作 `EB Send for Review` 送至 `EB Review`。
3. HR Manager 审核内容和范围；需要修改时点 `EB Return`，由 HR 修改后重新送审。
4. 审核通过点 `EB Publish`，进入 `EB Published`；HR User 不能发布，也不能直接改 is_published 绕过工作流。
5. 确认 X5 收到有效发布事件、Dify 文档索引完成后，再用可见及不可见岗位分别问一条合成问题。发布标记成功不代表同步或模型回答已通过。
6. 需要撤下时由 HR Manager 点 `EB Withdraw`，等待 X5 撤下并复测；不要只删除 Dify 里的副本，因为后续对账可能重新同步。
7. 对已发布内容重新编辑前先撤回为草稿，重新走送审及发布。不要直接编辑发布态规避审核。

## IT 配置国产模型、知识库和两个应用

1. 进入受管理员 IP 白名单保护的 Dify 后台。插件只选择 `langgenius/tongyi`、`langgenius/volcengine_maas`、`langgenius/deepseek` 等经批准的国产模型官方插件。
2. 按[模型插件验收](P0-模型插件验收.md)核对固定版本和安装包摘要，先在测试工作区验证；Key 在“设置 → 模型供应商”录入，不能写进 DSL、代码或截图。
3. 模型或插件升级前导出脱敏应用 DSL，记录原版本；在模型节点换为已配置国产模型，测试响应后发布。千问 → DeepSeek → 千问分别测试，Embedding 和 Rerank 另测。
4. 在“知识库”创建公司制度/受限资料库，选择批准的 Embedding；正式 high_quality 索引与 X3 hybrid_search 配套，测试 economy 用 keyword_search。更换 Embedding 先在测试库重建索引并验权限，不直接切生产库。
5. 进入“工具 → MCP”，登记 `http://frappe-mcp:8080/mcp/`，服务标识必须为 `eb-hr`；认证凭据从服务器私有文件取，在界面录入。
6. MCP 地址或 Token 变更后先点“授权”，再点“更新”，确认工具列表；新增工具也要更新。
7. “工作室 → 创建应用 → 导入 DSL”，导入 `config/dify/hr-assistant.yml`；制度问答使用 `config/dify/policy-qa.yml`。
8. 在 HR 助手“环境变量”填内网 X3/X4 地址及各自 Token，Token 保持 secret 类型；检查模型节点、MCP `eb-hr` 和知识库配置，发布两个应用。
9. 分别进入“HR 助手”和“制度问答”→“访问点”→ **Web App**，关闭开关并刷新确认已停用；**API 访问保持开启**。
10. 从管理员白名单内用无痕浏览器打开旧分享页，并刷新原聊天页尝试合成消息，应无法开始新请求；仅返回 Caddy 403 不能证明 Web App 已关闭。
11. 在“API 访问”生成 HR 助手应用 Key，仅填服务器 `DIFY_API_KEY`；用合成员工经 API/企业微信验证调用仍成功。
12. 每次复制、重新导入应用或升级 Dify 后，复查两个 Web App 均关闭。员工身份只取可信企业微信 userid，不拿控制台访客身份代测。

## 离职、账号停用和配置交接

1. HR Manager 先办理下属移交和未完审批，确认离职人员对应的 Employee 与 User 绑定准确。
2. 将 Employee 状态改为 Left，保存后检查关联 User 已禁用、旧会话失效；不要通过删除员工档案处理离职。
3. 通讯录自动离职必须先由 IT 确认完整目录授权，并设置 `full_directory_verified`，流程见运维手册；缩小应用可见范围不能导致误停用。
4. 用离职测试账号登录及问助手，应被拒并提示“未找到你的在职员工信息”；结果只记通过/失败，不回传个人信息。
5. 接口账号默认禁用且没有 Key。启用 X3/X4/X5 时分别生成各自 Key/Secret，仅授予表中角色，在服务器录入；轮换后用合成请求核对旧凭据失效。
6. 角色、字段、Workflow 等共享配置先在测试环境修改，再按[导出约定](P1-X1知识空间与Wiki同步.md#配置与验收证据)用 `enterprise_base.integration.export_configuration` 导出，核对 App fixtures 和 `config/frappe/` 后提 PR、空库导入复测。
7. 客户员工、真实模板、身份绑定、岗位开关选择及密钥属于私有业务数据，留客户数据库和加密归档；不得把生产 User、Employee、sites 配置混入共享 fixtures。

## 每次配置完成后的验收

使用合成数据逐项记录“通过/失败/待测”、版本和北京时间。截图位置统一为“待服务器截图”，实测后由 JQ 补充脱敏截图。

| 检查 | 通过标准 |
| --- | --- |
| 组织导入 | 错一行整批不写；重复导入不重复建档；抽查任职正确 |
| 权限 | HR User 读取/导出他人档案没有敏感字段，本人及 HR Manager 可按权限读取 |
| 知识范围 | 允许岗位能检索，未授权、无岗位和离职身份拒绝 |
| 岗位开关 | 关闭功能被拒；已起草后关闭也不能确认 |
| 请假 | 两级指定人分别审批；主管通过不扣余额，HR 通过只扣一次；非指定人/自批拒绝 |
| 入职 | 招聘前置齐全才出待办；重复保存不重复；负责人本人办结 |
| 制度 | HR User 发布拒绝，HR Manager 发布后 X5 实收并索引；撤回能撤下 |
| 入口 | 两个 Web App 关闭且 API 可用；System Manager 密码+双因素，扫码拒绝 |
| 离职 | 用户禁用、旧会话和助手调用均拒绝 |

遇到问题先停用受影响的应用入口或功能，联系 IT；仅提供组件名、时间、状态和去标识错误码，不转发原始日志、员工正文、Key、Token 或完整回调 URL。
