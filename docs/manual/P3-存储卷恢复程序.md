# 存储卷恢复程序（P3-G2）

`deploy/restore_storage.py` 是完整恢复入口的内部模块，仍需后续接上 Qdrant 与 `make restore`。只能在 `restore_guard.prepared` 完成整包 SHA256 校验、确认新项目并持有独占锁后调用。它不会启停业务服务，也不会删除旧环境数据。

恢复范围为 Dify API 文件、插件 storage、Caddy 证书和启用过的企业微信会话。先复核全部应用已停写，目标容器标签、实际镜像及命名卷归属与新项目一致；拒绝绑定宿主目录、旧项目卷、共享卷及含文件/链接的非空卷。所有组件都通过归档和空卷检查后才写入，不能只检查第一项。创建恢复目标容器时应使用 `volume.nocopy`，避免镜像初始内容被自动复制进新卷；仅含空目录可以通过检查。

归档不在宿主机展开。程序拒绝绝对路径、上跳、设备/稀疏条目、重复项、链接下面的子项和指向归档外的硬链接；保留插件环境需要的符号链接。使用备份记录的 Frappe 镜像运行原生 tar，恢复 UID/GID 和权限。临时容器只有一个目标卷可写，根文件系统只读、无网络、不加载业务密钥文件，运行日志关闭。任何失败都停止后续卷写入并清理临时容器；失败的新环境须保持关闭，人工确认后清理并重建，不能直接接流量。

本机测试校验真实 tar 和 Docker 调用协议；`frappe-contract` 新增实际空卷演练，使用相同恢复函数核对合成文件内容、UID/GID、600 权限及插件符号链接。CI 通过前以 PR 状态为准，不把协议测试算作真实容器恢复。全套 Dify、插件运行、Caddy 证书续期和企业微信登录会话仍待 Claude 云端联测，耗时与服务器截图待补。无新增依赖，不修改上游源码或 `.github/`。
