# P1-G4 企业微信通讯录同步

在服务器 `sites/<站点>/site_config.json` 的 `eb_wecom_sync` 对象设置 `enabled: true`、`company`（现有 Frappe 公司名）、`corpid`、`app_secret`（自建应用）、`directory_secret`（通讯录同步 Secret）。文件仅服务账号可读，不进入仓库或命令历史。一个站点对应一家企业，启用后不要直接替换企业 ID 或公司；迁移须先审查身份绑定。

应用须能读取所需部门和成员姓名；通讯录 Secret 用于取得全企业成员 ID，不能互换。管理员先确认通讯录同步授权覆盖全企业，并完成下列反例后，才设置 `full_directory_verified: true` 开启自动离职停用；默认不会因缺人停用。缺配置则不运行，错误/分页不全则整批不更新并记录固定类别告警。

执行 App migrate 后，原生 scheduler 每小时运行；确保站点 scheduler 已启用。HR Manager 可通过已登录同源请求（带 CSRF）或自己的 Frappe API token，POST `/api/method/enterprise_base.wecom.sync.sync_now` 手动同步，无请求正文；不要将凭据写入示例或共享记录。返回仅有更新、离职、待建档、跳过数量，或 `failed`/`disabled` 标记。异常数量写入 `wecom_sync` 日志，不记录人员、请求或密钥。

只使用官方 [department/list](https://developer.work.weixin.qq.com/document/path/90208)、[user/simplelist](https://developer.work.weixin.qq.com/document/path/90200) 和通讯录专用 [POST user/list_id](https://developer.work.weixin.qq.com/document/path/96067)。不调用含电话、邮箱、头像的成员详情接口。完整 ID 列表用于区分“应用看不见”和“企业已删除”；应用可见范围缩小不会让在职员工变成 Left。

部门按只读唯一字段 `eb_wecom_department_id` 幂等更新，保留 Frappe 主键和既有知识范围引用。所有同步部门设为群组以容纳后续层级变化。英文逗号、缺父级、循环会跳过并计数。已有同名但未绑定部门会整批回滚，交管理员确认合并/绑定，不能按名称自动认领。多部门成员跳过，HR 明确单一归属后再同步；不要默认取第一个部门。

员工须由 HR 先建档并明确绑定唯一 `wecom_userid`；新成员只计入 pending，不按姓名猜身份，不创建 User。仅更新在职员工姓名和部门，不恢复停用账号或 Left/Inactive 状态。姓名按企业微信完整姓名存入 first_name/employee_name，清空 middle_name/last_name；不修改 User 姓名、岗位或敏感字段。删除成员仅设置 Left 并调用已有停用/会话撤销 Hook，HR 后续补离职日期和下属移交；不会虚构日期或改上级关系。

CI：真实 Frappe 双空库验证幂等、人工停用保持、离职停用、权限拒绝和敏感字段不写入日志；上游使用合成响应。新增字段由安装 Hook 创建，导出 fixture 随 PR 提交，再由第二空库导入。

上线前仍需实测：在测试企业新增/调整部门、修改姓名、重复同步；缩小应用可见范围确认不离职；删除测试成员确认 Left、用户停用且企业微信助手拒绝；模拟接口故障确保不更新。仅回传计数和通过/失败。当前无服务器，以上真实通讯录及助手联测待补。
