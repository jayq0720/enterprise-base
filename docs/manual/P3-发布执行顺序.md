# 发布执行顺序

`deploy/release_runtime.py` 供发布/回滚总入口在维护锁内调用，当前不是独立发布命令。先完成版本检查、备份和发布记录，再构建目标Frappe镜像、生成完整配置并解析实际镜像ID；新镜像缺失或拉取失败时不停止现有服务。

按原先运行的服务清单处理，已关闭的企业微信和可选接口服务保持关闭。禁止接管其它项目卷/网络；数据库、Redis、Qdrant镜像必须与原部署ID一致，这些持久化引擎的升级须另做兼容性演练，本入口只处理应用发布。冻结配置文件600，镜像换成精确ID、`pull_policy=never`，不在迁移途中隐式拉取或构建。

执行顺序为数据库/缓存健康 → configurator与目标backend一致 → backend启动 → 持久标记需要数据库回退 → 全站点迁移 → Frappe队列/前端/调度 → Dify → X3/X4/X5 → 企业微信及Caddy → 自检。任何一步报错立即停止后续步骤，由总入口记录失败并提示回滚。

自检核对原先启用的全部服务及健康状态，读取Dify、Frappe登录页与已启用X3/X4/X5的健康端点，仅打印组件和HTTP状态。探针走容器内网，避免把管理员公网白名单拒绝当作故障；它不能代替外网白名单和企业微信联测。

发布准备同时修正App构建文件的组名：固定版官方Frappe镜像的frappe用户属于gid0，不能COPY给不存在的frappe组。原生CI增加实际App镜像构建，并用该镜像跑原有双空库及恢复测试；结果以PR所附CI为准。Docker协议测试另验证顺序、迁移前标记、出错停止、禁用服务保持、数据库升级拒绝及敏感输出隔离。没有新增依赖，不改上游或.github/。
