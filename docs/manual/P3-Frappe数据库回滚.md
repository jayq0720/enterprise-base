# 迁移后的 Frappe 数据库回滚

`deploy/restore_frappe_existing.py` 是回滚总入口的容器内执行部分，供已有站点数据回退使用；不是员工接口或独立运维入口。只有主机维护入口持有操作锁、明确指定覆盖、完成两次人工确认、核验发布记录及加密备份，并停止应用写入后才能调用。容器脚本还要求与目标站点一致的 `EB_RESTORE_EXISTING_APPROVED` 标记以避免误调用；标记不替代主机确认或数据库权限。

有迁移的发布必须恢复发布前数据库。将丢失发布后产生的数据，操作者须知道备份时间，不能只切回旧镜像或逆向执行迁移。新项目演练仍使用 `make restore`，默认不覆盖已有站点。

回退只从备份配置复制两项解密密钥，已有站点数据库名、密码、连接主机及其它私有配置保持目标值。SQL恢复前暂停调度、邮件和卡片；先移除公开/私有附件目录再由原生bench恢复，避免发布后新增文件残留。SQL恢复后核对数据库身份，执行旧版迁移、重设目标管理员密码、退出原管理员会话。全部成功后恢复目标原先的通知配置；失败保持暂停并停止后续操作，由主机总入口保持服务关闭。

成功和失败均尝试移除原生解包临时tar，不输出命令、凭据或业务记录。原始数据库恢复错误优先于清理错误。任何失败的新环境不能当成回滚成功；修改后重试仍须二次确认，重新恢复整个备份。

本机协议测试验证目标凭据不被覆盖、附件先清理、通知暂停/恢复、失败停止及输入拒绝。原生CI另在已经恢复的合成站点里修改岗位开关、新增岗位和文件，再恢复同一站点；核对发布后新增记录/附件消失、原记录数和附件SHA256一致、加密凭据及独立数据库身份仍正确。CI结果以PR记录为准，不把协议替身当成数据库回滚证明。

此模块只实现Frappe段；PostgreSQL、Qdrant、文件卷、版本恢复、入口和二次确认仍由完整回滚流程接入。没有新增依赖，不改上游或.github/；真实企业微信/审批卡片及正式切换仍待服务器联测。
