# 完整隔离恢复（P3-G2）

日常操作统一见[部署运维手册](部署运维手册.md#在新项目恢复备份)，本篇保留恢复机制、故障处理及开发验收证据。

`make restore` 只恢复到新的项目和目录，原环境继续运行。准备精确镜像、备份代码提交及离线 age 工具，见[恢复目录准备](P3-恢复目录准备.md)与[每日备份](P3-每日备份.md)。恢复机须有 Docker Engine ≥28、Compose、Git、uv 和足够磁盘；同时留出解密暂存及新卷空间。私钥由 JQ 临时挂载为本人所有的 600 文件，不能放入 `deploy/secrets/`，结束后卸载离线介质。备份文件也必须为本人所有的 600 文件。

入口持有与备份共用的操作锁，真实 age 解密并校验全部摘要后准备独立 worktree。先建空卷和数据库，恢复 PostgreSQL、Qdrant 全快照、Dify 文件/插件、Caddy 证书及已有企业微信会话，再用原生 bench 恢复每个 Frappe 站点并迁移。仅复制 Frappe 两项解密密钥，数据库名和密码重新建立，管理员使用目标新密码并退出原管理员会话。原版代码、原镜像 ID 与数据对应，不自动重建或拉取替代镜像。

验收副本只监听 `127.0.0.1:18080`。打开 `http://dify.eb-restore.localhost:18080` 与 `http://hr.eb-restore.localhost:18080`；更换项目/端口后相应替换。远程测试机使用 SSH 本机端口转发。Frappe 目录仍是原站点名，前端已作映射；新管理员密码仅在副本 `deploy/secrets/.env`，通过本机安全工具读取，不贴终端日志、PR 或聊天。

完成时所有启动服务须通过 Compose 等待检查，并确认 Frappe ping 和 Dify 首页 HTTP 正常。`deploy/data/restores/<项目>/deploy/data/restore-result.json` 的 `state=ready` 仅表示该检查通过。队列、定时任务、邮件、企业微信、X3/X4/X5 保持关闭，副本不自动重启；这不代表知识检索、模型调用或企业微信联测通过。Claude 还须核对员工/岗位/请假记录数、附件 SHA256、Dify 工作流和插件、Qdrant 集合/别名/检索以及 X3/X4/X5，记录整套恢复耗时，截图暂标“待服务器截图”。验收后启用后台服务须另作正式切换方案，不能直接运行普通 `make up`。

失败退出码非零，只打印组件及异常类型；先尝试停止本次创建的三个项目容器，再释放锁。`restore-result.json` 记为 `failed`，`stop_failed` 非空时必须人工确认这些副本已停服。容器内临时输入在结束时删除，宿主机解密暂存区总是清理；失败副本的私有配置和业务卷保留供本机排查，不能上传为 CI 附件。修复前换新项目重试，不往半成品追加恢复。

SIGTERM/SIGINT 延迟到安全边界，随后停服并清理；不要强杀。断电/SIGKILL 无法保证清理，重启后先确认没有操作进程，停用本次副本，清理 `deploy/data/.restore-clear-*` 和副本容器临时层残留。退出后取走解密介质；清理失败副本时只按该次新项目及其 worktree 清理，不对原项目执行 `down -v`。

生成的 `restore-*.json` 含凭据，文件权限 600，不展示或上传内容。手工查看状态也须使用冻结 JSON、新项目名和 `--pull never`；普通 Compose 文件会还原默认端口及部分生产配置。本次不安装 timer、群机器人或切换正式入口。没有新增依赖；真实 age/锁/信号/HTTP 和 Docker 协议测试在本机与 CI 验证，完整业务容器联测由 Claude 云端补录。
