# P2-G2 审批卡片部署与验收

仅在独立测试环境进行。前置 #51、#53–#57 全部通过 CI、Claude 审核并由 JQ 合并后，再从 main 构建和迁移；当前仍待 CI 和企业微信实测。沿用 P1 的唯一 userid 绑定和同一企业微信自建应用，不另占普通聊天的回调 URL。

在服务器 `deploy/secrets/.env` 填现有 WECHATCOM_CORP_ID、WECHATCOMAPP_AGENT_ID、WECHATCOMAPP_SECRET、WECHATCOMAPP_TOKEN、WECHATCOMAPP_AES_KEY 和 Dify API Key，禁止贴出。Token/AES/企业/应用必须与原聊天应用一致，AES 为 43 位，Agent ID 为数字。域名须 HTTPS，管理后台白名单继续生效。先保持 EB_WECOM_CALLBACK_MODE=bridge：

```sh
cd deploy
make build
make up
make wechat
```

先确认普通聊天正常。在 Frappe 给测试员工配置直属审批人、HR 审批人，二者均在职、账号已启用、有 Employee 和对应审批角色；审批人不能是申请人。再在私有 `.env` 把 `EB_WECOM_CALLBACK_MODE` 改成 `approvals`：

```sh
uv run --python 3.12 python wecom_cards.py secrets/.env --check
make wecom-cards
make status
```

目标先校验私有文件 600 权限、凭据格式及所有前置模块/DocType/Workflow/事件 Hook，将配置通过容器 stdin 写入已有站点的 `eb_wecom_cards`，不把密钥放入命令参数；不覆盖其它站点配置。然后重建后端、队列、调度器、前端和 Caddy。仍需在企业微信后台保存原 `https://wecom.<客户域名>/wxcomapp` 做 GET 验签；地址不变。站点 desk_url 从环境域名生成。

Caddy 仅公开精确 `/wxcomapp`，重写为唯一分发方法，删除 Cookie/认证/站点伪造头，限制 64 KiB。其他路径 404，不开放 HR 整站。Frappe 前端仍按原配置指定 `hr.<域名>` 站点。为避免官方 Nginx 和 Frappe 请求日志记录完整查询串，审批模式不持久化前端容器输出，并关闭站点请求日志/请求监控；审批审计仍保留在工作流记录及仅单号/动作/结果的卡片日志。不要开启原始请求追踪或导出回调正文。

验收逐项记录北京时间、main 提交、脱敏单号、结果；不要贴 userid、卡片内容、签名或凭据：

1. 真实普通聊天继续回复，身份仍匹配原在职员工。
2. 员工和 X4 各起一单：上级收到卡片，通过后 HR 收到第二张；HR 通过后 Approved、余额正确，两张卡显示完成和处理人。
3. 上级和 HR 分别退回；后台办理也更新对应卡片。重复点击只办一次，原生记录的 modified_by 为真实办理人。
4. 改签名/非当前审批人/自批/离职用户点击全部拒绝，状态不变。离职测试也核对后台用户禁用及助手的在职提示。
5. 从管理员白名单外访问 Dify/HR（含 /v1 和 /login）仍 403；wecom 域名的 /login、/api/resource/Employee、/wxcomapp/ 都 404。IPv4/IPv6 仍按原后台入口清单实测。

本地配置/Caddy 测试不等于以上联测。无测试服务器时全部留待测，禁止勾选收卡验收。发送最多三次受控尝试；不确定的超时不会立即自动重发。更新凭证有效 72 小时，过期显示 Expired，不能把审批改回未办。

回退：私有文件改回 `EB_WECOM_CALLBACK_MODE=bridge`，再执行 `make wecom-cards`，关闭卡片发送/动作并恢复原聊天路由；已有请假单继续由有权限的审批人在后台办理。保留数据卷和密钥，不执行 `down -v`。
