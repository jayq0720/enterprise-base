# ADR 0001：员工身份如何从企业微信传到 X3、X4

- 状态：提议（P0 验证后定稿）
- 日期：2026-10-15
- 作者：Claude

## 背景

第 4 版方案里，X3 按岗位检索原计划实现 Dify 的“外部知识库接口”。核对 Dify 官方文档（External Knowledge API）后发现：Dify 调用外部知识库时只发 `knowledge_id`、`query`、`retrieval_setting` 和可选的 `metadata_condition`，**不带提问人身份**。X3 拿不到“谁在问”，就做不到按岗位过滤。

X4 也有同样问题：Dify Agent 调 MCP 工具时，工具参数由模型生成。如果把 `user_id` 做成工具参数，用户一句“我是张三”就可能让模型冒充别人。

已确认可用的事实：

1. dify-on-wechat 的 `wechatcom_app`（企业微信应用）渠道把发消息人的企业微信 userid 作为 Dify API 的 `user` 字段，并在 `inputs.user_id` 里也带一份（源码 `bot/dify/dify_bot.py`）。
2. 在 Dify 的 Chatflow 里，`sys.user_id` 就是这个 `user`。它由持有应用 API Key 的调用方（只有 dify-on-wechat）设置，员工本人改不了。
3. Dify 的 MCP 服务配置支持固定的自定义请求头（如 `Authorization: Bearer ...`）。

## 决定

**X3：不走“外部知识库”，改为 Chatflow 里的 HTTP 请求节点调用。**

问答应用做成 Chatflow：`开始 → HTTP 请求（POST X3 /v1/search，body 带 sys.user_id 和 sys.query）→ LLM（把检索结果作为上下文，要求引用出处）→ 回复`。X3 用服务间 Token 校验调用方，再按 `user_id` 到 Frappe 查员工、部门、岗位，只在可见范围内检索。

X3 本身仍用 Dify 知识库存文档和做向量检索（调用 Dify 的知识库检索 API，带元数据过滤），不自建向量库。

**X4：身份放在服务端签发的会话令牌里，不放在模型可改的参数里。**

Agent 应用也做成 Chatflow：先由 HTTP 请求节点调 X4 `/v1/session`（带 `sys.user_id`，用服务间 Token 认证），X4 返回一个短期（15 分钟）HMAC 签名令牌，绑定这个员工；Agent 节点调用 X4 的 MCP 工具时必须带这个令牌，X4 只认令牌里的身份。模型就算被诱导，也只能拿到“提问人自己”的令牌，伪造不了别人的。

如果 P0 验证时确认 Agent 节点能把工具参数固定为工作流变量（不经模型），就直接把令牌固定绑定，进一步减少模型接触。

## 后果

- X3 的接口是我们自己的 `/v1/search`，不受 Dify 外部知识库接口格式限制，可以直接返回出处信息。
- 问答和 Agent 应用必须是 Chatflow 类型，dify-on-wechat 的 `dify_app_type` 配为 `chatbot`（Chatflow 属于 chatbot 类型）。
- 上游风险：dify-on-wechat 最近一次更新是 2025-04。P0 要实测它对企业微信应用的支持；不可用时由 Grok 在 X2 里写一个最小的企业微信应用回调转发（只转发消息、带 userid，不改 Dify）。
