# 任务卡 P1-G7：把 X3、X4 加进部署，接好 Dify

- 负责：GPT　审核：Claude　验收：JQ
- 分支：`gpt/P1-G7-deploy-x3-x4`，目标分支 `main`
- 背景：X5（policy-sync）已经在 `deploy/frappe-services.yaml` 里。X3 按岗位检索（`services/kb_gateway/`）和 X4 员工 HR 查询（`services/frappe_mcp/`）的代码和镜像已就绪，但还没进部署。HR 助手（`config/dify/hr-assistant.yml`）要用到这两个服务。

## 要做的事

1. **镜像**：Claude 的 CI 在合入 main 后，把三个服务的镜像都推到 GHCR：`enterprise-base-kb-gateway`、`enterprise-base-frappe-mcp`、`enterprise-base-policy-sync`。摘要在 Actions 的产物里。部署时和 policy-sync 一样，用 main 构建的 `@sha256:` 摘要，写进 `.env.example` 和 `VERSIONS.md`。
2. **两个服务**，照 policy-sync 的写法，加 `kb-gateway` 和 `frappe-mcp`：
   - 在 `deploy/frappe-services.yaml` 或 compose 里都可以，二选一并写明理由。
   - 健康检查都用 `GET /healthz`。
   - 不对公网开放，只在内部网络里供 Dify 访问。
   - 配置从 `deploy/secrets/kb-gateway.env`、`deploy/secrets/frappe-mcp.env` 读，`prepare.py` 负责生成随机 Token。变量名见两个服务目录下的 README 和 `config.py`，前缀都是 `EB_`。
   - X3 用 `eb-x3@integration.invalid` 的 Key，X4 **必须用 `eb-x4@integration.invalid` 的 Key**（只有它的权限是按 X4 收紧过的）。Key 由管理员在 Frappe 后台启用账号、生成后填进密钥文件，不进仓库。
   - `EB_MCP_ALLOWED_HOSTS` 填 Dify 访问 X4 用的主机名和端口，例如 `["frappe-mcp:8080"]`。
3. **Dify 能访问到这两个服务**：
   - Dify 的 api/worker 和 X3、X4 要在同一网络，或者走 Caddy 内部地址。
   - Dify 的 SSRF 代理默认拦内网地址，要放行 `kb-gateway`、`frappe-mcp`（和 policy-sync 一样）。改完要重建 `ssrf_proxy` 容器。
4. **Dify 后台初始化步骤**写进 `docs/manual/`。脚本能做的就做成脚本，做不了的写清楚点哪里：
   - 工具 → MCP → 添加：地址 `http://frappe-mcp:8080/mcp/`，**服务标识填 `eb-hr`**，请求头 `Authorization: Bearer <X4 的 EB_MCP_SERVICE_TOKEN>`。
   - X4 升级新增工具后，要在这个 MCP 服务上点“更新”。
   - 导入 `config/dify/hr-assistant.yml`，在环境变量里填 `x3_url`、`x3_token`、`x4_url`、`x4_token`，然后发布。
5. **`make verify`** 补上两个新服务的配置校验。部署隔离校验要覆盖：两个服务不对外暴露、密钥文件不进仓库。

## 验收

- 空服务器照 `LOCAL.md` 部署后，三个服务都健康。
- 在 Dify 里给 HR 助手发“我的岗位职责是什么”“我还有几天年假”，能拿到本人的数据。
- 跑一遍端到端测试 `tests/e2e`（见那里的 README），把结果贴进 PR。没有模型 Key 时可以不配 `EB_E2E_HR_APP_KEY`。
- PR 里附一次部署成功的日志摘要（去掉密钥）。
