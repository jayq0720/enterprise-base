# 任务卡 P2-G5：健康检查与告警

- 负责：GPT　审核：Claude　验收：JQ
- 分支：`gpt/P2-G5-monitoring`，目标分支 `main`
- 编号说明：GPT 任务清单原来把监控编为 P2-G3，这个编号已经用给了岗位助手功能开关，监控改为 P2-G5。
- 背景：上线后没人盯着控制台，服务挂了、磁盘满了要能主动通知。默认做法是一个轻量检查脚本加定时任务，告警发到企业微信群机器人，不引入一整套监控平台。如果 GPT 认为开源工具（例如 Uptime Kuma，MIT）更合适，在 PR 里说明理由，告警地址要在它的后台或服务器密钥文件里配置。

## 1. 检查项

| 检查 | 默认阈值（都做成配置） |
| --- | --- |
| 三套 Compose 里每个容器在运行、健康检查为 healthy | 任一不健康 |
| Dify、Frappe 登录页，X3/X4/X5 健康接口的 HTTP 状态 | 非 2xx 或超时 10 秒 |
| 磁盘：数据卷所在分区可用空间 | 低于 15% |
| 内存：可用内存 | 低于 10% |
| 最近一次备份（P3-G2）的时间 | 超过 26 小时 |
| Frappe 后台任务队列积压、调度器停止 | 调度器停止或积压超过阈值 |
| HTTPS 证书剩余天数（启用 https 时） | 少于 14 天 |

## 2. 告警

- 发到企业微信群机器人：Webhook 地址只放 `secrets/.env`（例如 `EB_ALERT_WECOM_WEBHOOK`），`.env.example` 留空，代码里不写地址。没配置时只写本机日志，不报错退出。
- 同一个问题持续时不重复刷屏：首次告警，之后每小时最多一次；恢复时发一条“已恢复”。
- 告警内容只写组件名、检查项、数值和时间，不写员工内容、userid、密钥或完整日志。

## 3. 入口

- `make health`：手动跑一次全部检查，打印每项通过/失败。
- 手册给出 systemd timer（或 cron）安装步骤，默认每 5 分钟跑一次，由 JQ 在服务器上执行。

## 验收

- 停掉一个容器、把磁盘阈值调高，都能收到告警；恢复后收到“已恢复”，期间不重复刷屏。
- 没配 Webhook 时脚本正常结束，只写日志。
- 单元测试覆盖阈值判断、防刷屏和“告警内容不含敏感字段”；在 CI 里用模拟的 HTTP 服务测告警发送，不调真实企业微信。
- 手册 `docs/manual/` 补“监控与告警”一节。
