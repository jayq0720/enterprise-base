# 任务卡 P1-G3 – P1-G5：X2 企业微信对接

- 负责：GPT　审核：Claude　验收：JQ
- 分支：每项一个 PR，`gpt/P1-G3-wecom-login`、`gpt/P1-G4-wecom-sync`、`gpt/P1-G5-dify-on-wechat`，目标分支都是 `main`
- 代码放 `frappe_apps/enterprise_base/enterprise_base/wecom/`（X2），企业微信入口配置放 `config/dify-on-wechat/`
- 前提：企业微信的企业 ID、应用 Secret、通讯录 Secret、回调 Token 和 EncodingAESKey 由管理员在 Frappe 后台录入或放服务器密钥文件，代码和仓库里一律没有。回调要已备案域名，没有时先用测试企业或内网穿透验证，PR 里写明。

## P1-G3 企业微信扫码登录 Frappe

- 用 Frappe 自带的 Social Login Key，或 X2 里的最小扩展。员工扫码后按企业微信 userid 找到 Employee 的 `wecom_userid`，再登录对应的 User。
- 找不到在职员工的 userid 不能登录，也不能自动建用户。
- 测试：未绑定的 userid、离职员工（状态 Left）登录被拒。

## P1-G4 通讯录同步

- 定时（默认每小时）加手动触发，从企业微信同步部门和成员到 Frappe HR。
- **只取部门、姓名、userid、所属部门**。手机号、邮箱、头像等一律不取、不落库、不进日志。
- `wecom_userid` 写进 Employee。X3、X4 只认这个字段，而且必须唯一。
- 企业微信里离职或删除的成员：Employee 设为 Left（P2-G 已做的离职停用会接着禁用用户），不删记录。
- 部门名同步时检查不含英文逗号，有就报警跳过，不能改坏 `eb_scope`。
- 测试：同步结果和日志里没有手机号；重复同步不产生重复记录；离职成员变 Left。

## P1-G5 dify-on-wechat 接企业微信应用

- `config/dify-on-wechat/config.json` 接 HR 助手（`dify_app_type` 用 `chatbot`，Key 放密钥文件）。
- **必须实测并在 PR 里写结果**：
  1. Dify 收到的 `user` 正好是员工的企业微信 userid（X3、X4 只按它查人，见 `docs/adr/0001-身份传递.md`）。
  2. 同一个员工连续发的消息沿用同一个 Dify 会话。请假草稿存在会话变量里，换了会话“确认请假”就会失败。做不到的话告诉 Claude，Claude 改 HR 助手的存法。
  3. 回调验签失败、未知 userid 的消息被拒或收到“未找到你的在职员工信息”。
- dify-on-wechat 2025-04 后没有更新。如果实测有问题，先写清楚现象交 Claude 和 JQ 决定，不改它的源码。

## 验收

- 员工扫码登录 Frappe；同步后库里没有手机号。
- 企业微信里问“我的岗位职责是什么”“年假规定”，收到的是本人的结果。
- 发起请假，回复“确认请假”后 Frappe 里出现请假单。
