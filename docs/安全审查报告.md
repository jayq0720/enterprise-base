## 2. 问题

### 2.1 S1：Web App 能冒充员工

- **怎么发生：** Dify 1.17.1 发布应用时默认开启 Web App（一个浏览器网址）。Web App 支持在网址上带 `sys.user_id=…` 参数（`web/app/components/base/chat/utils.ts` 的 `getProcessedSystemVariablesFromUrlParams`），后端换通行证时用这个值作为终端用户的会话 ID（`api/controllers/web/passport.py` 的 `user_id`）。工作流里 `sys.user_id` 就是这个会话 ID。
- **后果：** 能打开这个网址的人，只要知道同事的企业微信 userid，就能以同事身份查假期余额、请假记录、待审批、岗位职责、能看的制度，还能替同事起草并确认请假。
- **谁能打开：** Dify 整站受管理员来源白名单限制（`EB_ADMIN_ALLOW_CIDRS`）。如果白名单填的是公司办公网出口，公司里任何人都能打开。
- **处理：** HR 助手和制度问答只走企业微信（dify-on-wechat 用服务 API 和应用 Key），不需要 Web App。部署时在 Dify 应用“概览”里把“Web App”关掉，只保留“后端服务 API”。
  - 需要 GPT 在 `docs/manual/P1-HR助手部署与验收.md` 的发布步骤加这一条，并在验收里检查 Web App 网址打不开。
  - 服务器实测时用一个合成员工确认：开着 Web App 时能冒充（证实问题），关掉后网址返回不可用。
- **不受影响的部分：** 企业微信这条路上，`sys.user_id` 由 dify-on-wechat 按企业微信回调里的 userid 填，回调有企业微信签名，员工改不了。

### 2.2 S2：Dify 应用编辑者等于能看所有员工数据

- **怎么发生：** X3、X4 只认服务 Token，Token 填在 Dify 应用的环境变量里（secret 类型，界面和导出都不显示）。但能编辑应用的人可以加一个 HTTP 节点，用这个 Token 直接调 X4 `/v1/session` 给任意 userid 换会话令牌，或调 X3 按任意 userid 检索。ADR 0001 的信任边界本来就是“Dify 工作流可信”。
- **处理：** Dify 工作空间只给系统管理员（JQ 指定的人）开账号，不给 HR 和普通员工开编辑权限。已在下面第 3 节和权限复核表里列为上线条件。以后要给业务人员开 Dify 编辑权限，要先改成每个应用单独签发、只能调指定接口的 Token。
- **不扩大：** SSRF 代理只放行 `kb-gateway`、`frappe-mcp` 两个内网名字，工作流不能直连 Frappe、X5 或数据库。

### 2.3 S3：Actions 引用改为固定哈希

`actions/checkout`、`actions/upload-artifact`、`actions/cache`、`astral-sh/setup-uv` 原来写 `@v4`/`@v5`，这些标签可以被改指向别的提交。本 PR 改成当前标签对应的 40 位提交哈希，注释里保留版本号。gitleaks 镜像已固定到 `v8.21.2`。

## 3. 逐项核对

### 密钥

| 项目 | 结果 |
| --- | --- |
| 仓库里有没有密钥 | 没有。CI 每次跑 gitleaks（含全部历史）。`.env.example` 只有 `CHANGE_ME` 和镜像摘要 |
| 服务密钥从哪来 | 都从服务器 `secrets/` 下的环境文件读，`make init` 随机生成，至少 32 位；X3/X4/X5 各用自己的 Token 和 Frappe 账号，相同会拒绝启动 |
| 模型 Key、Dify 知识库 Key | 只在 Dify 后台录入，不进仓库、不进环境变量模板 |
| Dify DSL | `x3_token`、`x4_token` 是 secret 类型，导出时为空 |
| 程序里怎么用 | 用 pydantic `SecretStr` 保存，比对用 `hmac.compare_digest`，不打印 |

### 权限

| 项目 | 结果 |
| --- | --- |
| 员工身份 | 只认 `sys.user_id`；模型只能填 X4 签发的会话令牌，伪造不了别人的（HMAC-SHA256，15 分钟过期，用途分开） |
| 请假提交 | 草稿令牌绑定员工和草稿内容，10 分钟过期；提交时再核对 userid 和员工编号；重复确认会被 Frappe 的时间重叠校验拒绝 |
| 集成账号 | eb-x3 只读组织和知识空间；eb-x4 只能读 Employee 少数字段、按名查岗位职责、建请假单；没有 HR Manager/System Manager |
| 导入接口 | 只有 HR Manager/System Manager 能调；改 userid 和知识空间还要 HR Manager；整批校验、失败回滚 |
| 后台入口 | Dify、Frappe 后台都有来源白名单；企业微信回调只开 `/wxcomapp` 路径 |

### 日志脱敏

| 项目 | 结果 |
| --- | --- |
| X3/X4/X5 自己的日志 | 只写错误类型、页面编号、数量，不写问题、制度正文、员工数据、Token |
| httpx 请求日志（含 userid 的网址） | X4 显式压到 WARNING；X3、X5 没开根日志的 INFO，也不会打印。以后有人调日志级别时要注意 |
| X1 导入 | 错误只返回表、行、列和原因，不回传单元格内容和原始异常，有测试 |
| 访问日志 | uvicorn 只记路径和状态码；接口都是 POST，参数不在网址里 |

### 敏感字段

| 项目 | 结果 |
| --- | --- |
| 读 Frappe | X3、X4、X5 都指定字段列表，不用 `*`；手机号、身份证号、银行卡、薪资不在任何列表里 |
| 进模型 | 余额、请假、职责走代码节点整理后直接回复，不进模型；模型只看问题和检索到的制度 |
| 导入 | 表头出现敏感列整批拒绝 |
| 字段权限 | 敏感字段在 Frappe 是 permlevel 1，集成账号没有这一级权限（P2-G） |

### 外部接口登记

| 接口 | 谁调 | 认证 | 在哪配置 |
| --- | --- | --- | --- |
| X3 `/v1/search` | Dify HTTP 节点 | Bearer 服务 Token | 服务器密钥文件 + Dify 环境变量 |
| X4 `/v1/session`、`/v1/leave/confirm`、`/mcp/` | Dify HTTP 节点、MCP 工具 | Bearer 服务 Token；MCP 另校验 Host | 同上 + Dify“工具 → MCP” |
| X5 `/v1/hooks/wiki` | Frappe Webhook | HMAC 签名（只推页面编号，X5 回读） | 服务器密钥文件 + Frappe Webhook |
| X5 `/v1/reconcile` | 运维手动或定时 | Bearer 服务 Token | 服务器密钥文件 |
| Frappe REST | X3、X4、X5 | 各自专用账号的 API Key | Frappe 后台生成，填服务器密钥文件 |
| Dify 知识库 API | X3、X5 | 知识库 API Key | Dify 后台生成，填服务器密钥文件 |
| 模型 | Dify | 模型 Key | Dify 后台“模型供应商”，只用国内模型 |
| 企业微信 | dify-on-wechat、X2 | 企业微信应用凭据 | 服务器密钥文件（X2 待做） |
